00왜 훅 선택이 8할인가

잘못 고르면 코드가 아무리 좋아도 소용없다.

훅을 잘못 고르면 생기는 일

잘못된 선택결과
시스템콜에 kprobearm64 에서 되던 게 x86 에서 안 된다 (__arm64_sys_* vs __x64_sys_*)
tracepoint 있는데 kprobe커널 업그레이드마다 조용히 깨진다
차단하려는데 tracepoint반환값이 무시된다. 아무것도 못 막는다
egress 보려는데 XDPXDP 는 ingress 전용. 이벤트가 하나도 안 온다
너무 얕은 지점connect(2) 진입에서는 목적지가 유저 포인터다. 구조체로 못 받는다
너무 깊은 지점내부 함수라 커널 버전마다 이름이 바뀐다

전부 코드를 다 짜고 나서야 발견되는 문제들이다. 그래서 순서를 뒤집어야 한다 — 찾고, 확인하고, 그 다음에 짠다.

이 랩이 강제하는 습관

채점기가 두 단계로 본다:

  1. 존재 검증 — 네가 적은 훅이 이 커널에 실제로 있는가. 없으면 정답 여부를 보기 전에 걸린다.
  2. 정답 검증 — 목표에 맞는 훅인가.
1번이 진짜 목적이다

실무에서 가장 흔한 실패는 "틀린 훅을 골랐다"가 아니라 "그 커널에 없는 훅을 가정하고 짰다"이다. 블로그에서 본 함수 이름을 그대로 썼는데 우리 커널엔 없거나 이름이 다른 경우다. 대상이 존재하는지 확인하는 명령을 손에 익히는 것이 이 랩의 전부다.

01훅 지도

전체 종류와 각각이 무엇과 거래하는가.

훅붙는 곳안정성할 수 있는 일랩
tracepoint커널이 공식 선언한 지점높음 (ABI)관찰02, 07
fentry / fexitBTF 에 있는 커널 함수높음 (틀리면 로드 거부)관찰 (+반환값)03, 07
kprobe / kretprobe아무 커널 함수낮음관찰01, 07
uprobe유저 바이너리의 심볼낮음 (패치마다 오프셋 변경)관찰04, 12
XDP드라이버 수신 직후높음드롭·리다이렉트 (ingress만)05, 11
TC / TCX네트워크 스택 (skb 있음)높음변조·드롭 (양방향)06, 08, 09, 14
LSM커널 보안 결정 지점높음차단 (-EPERM)10, 13

결정 트리

1) 관찰인가 차단인가?
     차단 ─ 파일/실행/소켓 ──▶ LSM
          └ 패킷 ────────────▶ XDP(ingress만) 또는 TC/TCX(양방향)
     관찰 ─▶ 2

2) 네트워크 패킷인가?
     ingress 만 + 최고속 ────▶ XDP
     양방향 + 메타데이터 ────▶ TC/TCX
     아니면 ─▶ 3

3) 유저 공간 함수인가?  ──────▶ uprobe
     아니면 ─▶ 4

4) tracepoint 가 있나?
     ls /sys/kernel/debug/tracing/events/
     있다 ───────────────────▶ tracepoint   ← ABI 로 유지된다. 최우선
     없다 ─▶ 5

5) BTF 에 그 함수가 있나?
     bpftrace -l 'kfunc:*이름*'
     있다 ───────────────────▶ fentry   ← 타입 안전 + 빠름
     없다 ─▶ 6

6) ────────────────────────▶ kprobe   ← 커널 버전마다 깨질 각오
한 단계 더 — "얕게 vs 깊게"

같은 이벤트라도 잡을 수 있는 지점이 여러 개다. 시스템콜 진입은 안정적이지만 인자가 유저 포인터라 내용을 복사해야 하고, 커널 내부로 내려가면 구조체를 통째로 받을 수 있지만 깨지기 쉽다.

예: TCP 연결 관측 — sys_enter_connect(안정적, sockaddr를 유저 메모리에서 복사) vs fentry/tcp_connect(struct sock *를 그대로 받음). 03번이 후자를 고른 이유가 이것이다.

02탐색 절차

이 명령들만 알면 다 찾는다.

tracepoint 찾기

ls /sys/kernel/debug/tracing/events/                    # 그룹 목록
ls /sys/kernel/debug/tracing/events/syscalls/ | grep openat
ls /sys/kernel/debug/tracing/events/sched/             # 스케줄러 이벤트

# 인자 레이아웃 = 계약서. 코드 쓰기 전에 반드시 본다
cat /sys/kernel/debug/tracing/events/syscalls/sys_enter_openat/format

fentry 대상 찾기

bpftrace -l 'kfunc:*tcp_connect*'      # 0.20 은 fentry 를 kfunc 라 부른다
# → kfunc:vmlinux:tcp_connect

# 시그니처 확인 — fentry 는 틀리면 로드가 거부된다
bpftool btf dump file /sys/kernel/btf/vmlinux format c | grep -w tcp_connect

kprobe 대상 찾기

grep ' [tT] do_unlinkat$' /proc/kallsyms
# 아무것도 안 나오면 그 함수는 없거나 인라인됐다

LSM 훅 찾기

grep ' [tT] bpf_lsm_' /proc/kallsyms | head -40
grep ' [tT] bpf_lsm_file' /proc/kallsyms      # 파일 관련
grep ' [tT] bpf_lsm_bprm' /proc/kallsyms      # 실행 관련

uprobe 대상 찾기

go tool nm /opt/lab/bin/workload | grep main.compute
nm -D /usr/lib/aarch64-linux-gnu/libssl.so.3 | grep SSL_write

# 아무것도 안 나오면: 스트립됐거나 인라인됐다

이 커널이 지원하는 것

bpftool feature probe | grep -i 'program_type'
# → eBPF program_type sched_cls is available  (= TC/TCX 가능)
# → eBPF program_type xdp is available

make check      # 이 랩이 필요한 커널 기능 38개를 한 번에 점검한다
bpftrace 는 짜기 전에 먼저 써 보는 도구다 
# 붙을 수 있는지 + 실제로 이벤트가 오는지 한 줄로 확인
bpftrace -e 'kfunc:tcp_connect { printf("%s\n", comm); }'
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

C 를 짜고 verifier 와 싸우기 전에 여기서 먼저 검증하면 시간이 크게 줄어든다. "이 훅에 이벤트가 오긴 하나?" 를 30초에 답할 수 있다.

03자주 하는 실수

채점기가 잡아내는 것들.

1 · 블로그에서 본 함수 이름을 그대로 쓴다

커널 버전이 다르면 없거나 이름이 다르다. 항상 /proc/kallsyms 나 bpftrace -l 로 이 커널에 있는지 확인하고 시작한다. 채점기의 "존재 검증" 단계가 정확히 이걸 강제한다.

2 · 시스템콜을 kprobe 로 잡으려 한다

실제 심볼이 아키텍처마다 다르다. 시스템콜은 무조건 tracepoint다. ls /sys/kernel/debug/tracing/events/syscalls/ 에 거의 다 있다.

3 · 차단하려는데 관찰용 훅을 고른다

kprobe·tracepoint·fentry 는 반환값이 무시된다. 막고 싶으면 결정 지점에 있는 훅이어야 한다 — 파일·실행·소켓은 LSM, 패킷은 XDP/TC. "이걸 막을 수 있나?" 는 훅을 고르기 전에 답해야 하는 질문이다.

4 · egress 를 XDP 로 보려 한다

XDP 는 ingress 전용이다. 나가는 패킷은 TC/TCX다. 이벤트가 하나도 안 오는데 코드는 멀쩡해 보여서 오래 헤맨다.

5 · 인자 레이아웃을 확인 안 하고 짠다

format 파일이 있는데도 안 본다. 이 랩의 README 에도 "args[0] 이 파일명" 이라고 잘못 적혀 있었다 — openat 은 args[1] 이 파일명이다(args[0] 은 dfd). 기억이나 문서 말고 format 파일을 믿어라.

다 풀었으면

make hunt-check     # 70점 넘으면 클리어
make 01             # 이제 코드를 짠다

01·02 는 훅을 미리 주고 개념에 집중한다. 03 번부터는 SEC() 이 비어 있어서 여기서 익힌 절차로 직접 찾아야 한다. 각 .bpf.c 의 🎯 Lv0 주석에 탐색 명령이 들어 있다.

04퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

점수 0 / 12 아직 안 풀었다

A. O / X

01시스템콜을 잡을 때는 kprobe보다 tracepoint가 낫다.

정답 O. 실제 심볼이 아키텍처마다 다르다(__arm64_sys_openat vs __x64_sys_openat). tracepoint 이름은 어디서나 같다.

02tracepoint 훅에서 0이 아닌 값을 반환하면 시스템콜을 막을 수 있다.

정답 X. 관찰용 훅은 반환값이 무시된다. 차단하려면 LSM처럼 결정 지점에 있는 훅이어야 한다.

03XDP로는 인터페이스에서 나가는(egress) 패킷을 볼 수 없다.

정답 O. XDP는 드라이버 수신 직후, 즉 ingress 전용이다. 양방향이 필요하면 TC/TCX다.

04BTF에 있는 커널 함수라면 fentry가 kprobe보다 낫다.

정답 O. 타입 안전(틀리면 로드 거부)하고 트램폴린이라 더 빠르다. kprobe는 tracepoint도 BTF도 없을 때의 마지막 수단이다.

05bpftrace -l 'kfunc:*tcp*'는 fentry로 붙을 수 있는 대상을 보여준다.

정답 O. bpftrace 0.20은 fentry를 kfunc라고 부른다. 코드를 쓰기 전 대상 확인에 쓴다.

06uprobe는 커널 함수에 붙는다.

정답 X. 유저 공간 바이너리의 심볼에 붙는다. go tool nm이나 nm -D로 심볼 존재를 먼저 확인한다.

07/proc/kallsyms에 없는 함수에도 kprobe를 붙일 수 있다.

정답 X. 심볼이 있어야 붙는다. 없으면 인라인됐거나 이름이 다른 것이다. 부착 실패의 1순위 원인이다.

08LSM 훅이 이 커널에 있는지는 bpf_lsm_ 접두사로 확인할 수 있다.

정답 O. grep ' [tT] bpf_lsm_file' /proc/kallsyms 같은 식이다. BPF LSM은 이 심볼들에 붙는다.

09같은 이벤트라도 시스템콜 진입과 커널 내부 함수 중 어디를 잡느냐에 따라 얻는 정보가 다르다.

정답 O. 시스템콜 진입은 안정적이지만 인자가 유저 포인터다. 커널 내부는 구조체를 그대로 받지만 깨지기 쉽다. 03번이 후자를 고른 이유다.

10tracepoint의 인자 레이아웃은 format 파일에서 확인할 수 있다.

정답 O. 오프셋과 타입이 그대로 적혀 있다. openat의 파일명이 args[1]인 것도 여기서 확인한다.

11훅을 고르기 전에 "이걸로 차단이 가능한가"를 먼저 답해야 한다.

정답 O. 관찰 훅으로는 절대 못 막는다. 코드를 다 짜고 나서 알게 되면 훅부터 다시 골라야 한다.

12블로그에서 본 커널 함수 이름은 대개 어느 커널에서나 그대로 쓸 수 있다.

정답 X. 커널 버전이 다르면 없거나 이름이 다르다. 실무에서 가장 흔한 실패가 "그 커널에 없는 훅을 가정하고 짠 것"이다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1이 커널에 do_unlinkat 이 실제로 있는지 확인하려면? 
grep ' [tT] do_unlinkat$' /proc/kallsyms

아무것도 안 나오면 없거나 인라인된 것이다. kprobe 부착 실패의 1순위 원인.

C2fentry 로 붙을 수 있는 대상을 찾으려면? 
bpftrace -l 'kfunc:*tcp_connect*'
# → kfunc:vmlinux:tcp_connect

bpftrace 0.20 은 fentry 를 kfunc 라고 부른다. tracepoint 가 없을 때 두 번째 선택지다.

C3파일 열기를 차단하는 LSM 훅이 이 커널에 있는지 확인하려면? 
grep ' [tT] bpf_lsm_file_open$' /proc/kallsyms

관찰이 아니라 차단이 목표라면 훅 후보 자체가 LSM으로 좁혀진다.
