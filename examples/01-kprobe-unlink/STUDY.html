ebpf-lab/예제 01/kprobe + ringbuf

주소에 박는 브레이크포인트

첫 번째 랩이다. 커널 함수 진입점에 훅을 박고, 거기서 만든 이벤트를 링버퍼로 하나씩 유저 공간에 올린다. Frida의 Interceptor.attach와 가장 가까운 방식이고, 동시에 eBPF에서 가장 잘 깨지는 방식이기도 하다. 왜 그런지까지가 이 랩의 내용이다.

00kprobe란 무엇인가

커널 아무 함수에나 붙을 수 있는 대신, 아무것도 보장해주지 않는 훅.

동작 원리 — 명령어를 바꿔치기한다

kprobe는 대상 함수의 첫 명령어를 트랩 명령으로 덮어쓴다. 그 함수가 호출되면 CPU가 트랩을 일으키고, 커널이 등록된 핸들러(= 내 BPF 프로그램)를 부른 다음, 원래 명령을 실행하고 돌아간다. 디버거의 브레이크포인트와 같은 원리다.

즉 커널 소스에 아무 준비가 없어도 붙을 수 있다. /proc/kallsyms에 심볼이 있으면 대상이 된다. 이게 kprobe의 유일하면서 결정적인 장점이다.

대가 — 아무것도 보장되지 않는다

  • 시그니처가 바뀌면 조용히 틀린다. do_unlinkat(int dfd, struct filename *name)의 인자 순서가 커널 버전에서 바뀌어도 컴파일은 된다. 대신 엉뚱한 메모리를 읽는다.
  • 함수가 사라지면 부착이 실패한다. 인라인되거나 이름이 바뀌면 그날로 끝이다.
  • 시스템콜에는 쓰면 안 된다. 실제 심볼이 아키텍처마다 다르다 — arm64 __arm64_sys_openat, x86_64 __x64_sys_openat.
  • 느리다. 트랩 → 예외 처리 경로를 탄다. fentry(03번)는 트램폴린이라 이 비용이 없다.

그럼 언제 쓰나

tracepoint도 없고 BTF에도 없을 때의 마지막 수단이다. 커널 내부 함수를 들여다봐야 하는데 다른 길이 없을 때. 실무 순서는 항상 이렇다:

  1. tracepoint가 있나? → ls /sys/kernel/debug/tracing/events/ (02번)
  2. BTF에 있나? → fentry (03번)
  3. 둘 다 없다 → kprobe, 그리고 커널 업그레이드마다 깨질 각오
Frida 사용자에게

Interceptor.attach(Module.getExportByName(null, "open"), {...})와 정확히 같은 모델이다. 주소를 찾아서 거기에 트랩을 박는다. 다른 점은 대상이 프로세스가 아니라 커널 전체이고, 핸들러가 JS가 아니라 verifier를 통과한 바이트코드라는 것. 그래서 Frida처럼 Memory.readUtf8String(ptr)을 바로 못 쓰고 bpf_probe_read_kernel_str()을 거쳐야 한다.

01이 랩이 하는 일

do_unlinkat에 붙어서 "누가 무슨 파일을 지웠나"를 실시간으로 올린다.

대상 함수

fs/namei.c의 int do_unlinkat(int dfd, struct filename *name). unlink(2)와 unlinkat(2) 두 시스템콜이 공통으로 도달하는 지점이라 여기 하나만 잡으면 파일 삭제를 다 본다. 시스템콜 두 개를 각각 잡는 것보다 낫다 — "공통 경로를 찾아 한 번만 훅한다"가 트레이싱의 기본 전략이다.

데이터 전달 — RINGBUF

파일 삭제는 드물게 일어난다. 그래서 이벤트 하나하나를 통째로 유저 공간에 올린다. (02번의 openat처럼 초당 수백 건이면 이 방식은 못 쓴다 — 그래서 거기선 집계로 바꾼다.)

링버퍼의 사용 순서는 항상 세 단계다:

e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);  // 1) 자리 예약 (실패하면 NULL)
if (!e) return 0;                                 //    verifier 필수 NULL 체크
/* ... e 의 필드를 채운다 ... */
bpf_ringbuf_submit(e, 0);                         // 3) 제출 (버리려면 discard)
왜 malloc 이 아니라 예약인가

BPF에는 힙이 없다. 링버퍼는 커널과 유저 공간이 공유하는 원형 버퍼이고, reserve는 "이 영역을 내가 쓸 테니 건드리지 마라"는 표시다. submit 전까지 유저 공간에는 안 보인다. 그래서 중간에 마음이 바뀌면 bpf_ringbuf_discard()로 버릴 수 있다 — Lv4 과제가 이걸 쓴다.

실행

# 터미널 A
make 01

# 터미널 B
make sh
touch /tmp/x && rm /tmp/x

# 채점
make 01-check

02단계 공략

빈칸 4개. 순서대로 뚫으면 된다. 각 단계가 무엇을 검증하는지 알고 가면 훨씬 빠르다.

LV 1 · 25점링버퍼 예약
e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);

채점 방법: 채점기가 파일을 만들고 rm으로 지운 뒤, 출력에 이벤트 행이 있는지 본다.

막히는 지점: if (!e) return 0;를 지우면 안 된다. verifier가 bpf_ringbuf_reserve의 반환을 "NULL일 수 있는 포인터"로 추적하기 때문에, 체크 없이 e->tgid를 쓰면 로드 자체가 거부된다.

LV 2 · 25점누가 지웠나
__u64 id = bpf_get_current_pid_tgid();
e->tgid = id >> 32;      // 유저가 말하는 PID (프로세스)
e->pid  = (__u32)id;     // 커널이 말하는 PID (스레드)
bpf_get_current_comm(&e->comm, sizeof(e->comm));

채점 방법: COMM 칸에 rm이 찍히는지 확인한다.

기억할 것: 상위/하위 32비트가 뒤집혀 있다. 직관과 반대라 한 번은 꼭 헷갈린다. comm이 16바이트인 건 커널 task_struct.comm 크기 그대로라서, 리눅스 프로세스 이름이 15자에서 잘리는 이유가 여기 있다.

LV 3 · 25점어떤 파일인가
const char *fname = BPF_CORE_READ(name, name);
bpf_probe_read_kernel_str(&e->filename, sizeof(e->filename), fname);

왜 두 단계인가: struct filename의 name 필드를 읽는 것(1단계)과, 그 포인터가 가리키는 문자열을 복사하는 것(2단계)은 완전히 다른 작업이다.

  • BPF_CORE_READ(name, name) — 구조체 필드 접근. CO-RE 재배치가 걸려서 필드 오프셋이 다른 커널에서도 동작한다. name->name으로 쓰면 오프셋이 박혀 버린다.
  • bpf_probe_read_kernel_str() — 문자열 복사. 직접 역참조는 verifier가 막는다. 커널 메모리라도 페이지 폴트 가능성이 있어서 안전한 헬퍼를 거쳐야 한다.
LV 4 · 10점커널 단계 필터 (보너스)

rm이 아닌 프로세스의 삭제는 버린다. 채점기는 rm과 find -delete로 각각 파일을 지운 뒤, rm 것만 올라오는지 확인한다.

/* comm 을 먼저 읽고, 아니면 discard */
if (e->comm[0] != 'r' || e->comm[1] != 'm' || e->comm[2] != 0) {
        bpf_ringbuf_discard(e, 0);
        return 0;
}

핵심은 discard다. 예약해 놓고 안 쓰면 submit도 discard도 하지 않은 채 리턴하는 실수를 하기 쉬운데, 그러면 verifier가 거부한다 — "예약한 건 반드시 처리하라"가 규칙이다.

03함정과 디버깅

이 랩에서 실제로 걸리는 것들.

함정 1 · 심볼이 없다

부착이 no such file or directory로 실패하면 함수가 없는 것이다. 먼저 확인하라:
docker compose exec lab grep ' [tT] do_unlinkat$' /proc/kallsyms
kprobe의 근본적 취약점이 이것이다. 커널이 바뀌면 이 확인부터 다시 해야 한다.

함정 2 · 이벤트는 오는데 값이 이상하다

링버퍼에서 예약한 메모리는 0으로 초기화되지 않는다. 이전 이벤트의 잔재가 그대로 남아 있다. 필드를 하나라도 안 채우면 쓰레기값이 유저 공간까지 올라간다. Lv2를 건너뛰고 Lv3만 채우면 이 현상을 직접 볼 수 있다 — 한 번 해볼 만하다.

함정 3 · _kernel 과 _user 를 바꿔 썼다

bpf_probe_read_user_str()을 여기서 쓰면 에러가 안 나고 빈 문자열이 나온다. do_unlinkat 시점엔 경로가 이미 커널로 복사된 뒤이기 때문이다. 반대로 시스템콜 진입 직후(sys_enter_*)라면 _user가 맞다 — 07번에서 둘 다 나온다.

커널 쪽 확인하기

# make 01 이 돌고 있는 상태에서, 다른 터미널
make progs                       # 로드된 BPF 프로그램 목록
make maps                        # 맵 목록 (events 링버퍼가 보인다)
make links                       # 어디에 붙어 있는지
make trace                       # bpf_printk 출력 (trace_pipe)

디버깅이 막히면 bpf_printk("here tgid=%d\n", e->tgid);를 박고 make trace로 본다. eBPF의 console.log다. 느리니 확인 후엔 지운다.

02번은 이 랩의 두 가지를 동시에 뒤집는다 — 훅을 안 깨지는 tracepoint로 바꾸고, 이벤트를 올리는 대신 커널 안에서 집계한다. 왜 그래야 하는지는 02번 문서의 첫 절에 있다.

04퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

점수 0 / 12 아직 안 풀었다

A. O / X

01kprobe는 커널 소스에 아무 준비가 없어도 붙을 수 있다.

정답 O. 심볼만 있으면 붙는다. 대상 함수의 첫 명령어를 트랩으로 덮어쓰는 방식이라 커널 쪽 협조가 필요 없다. 자유도가 높은 대신 아무 보장도 없다.

02kprobe로 openat 시스템콜을 잡는 것이 tracepoint보다 이식성이 좋다.

정답 X. 정반대다. 시스템콜의 실제 심볼은 아키텍처마다 다르다(__arm64_sys_openat vs __x64_sys_openat). 시스템콜은 tracepoint를 쓰는 게 정석이다.

03do_unlinkat 하나만 잡으면 unlink(2)와 unlinkat(2)를 모두 관측할 수 있다.

정답 O. 두 시스템콜이 공통으로 도달하는 구현부이기 때문이다. "공통 경로를 찾아 한 번만 훅한다"가 트레이싱의 기본 전략이다.

04bpf_ringbuf_reserve()가 돌려준 포인터는 NULL 체크 없이 써도 된다.

정답 X. verifier가 이 반환값을 추적한다. 체크 없이 역참조하면 로드가 거부된다. 버퍼가 꽉 차면 실제로 NULL이 온다.

05링버퍼에서 예약한 메모리는 0으로 초기화되어 있다.

정답 X. 초기화되지 않는다. 이전 이벤트의 잔재가 남아 있어서, 안 채운 필드는 쓰레기값 그대로 유저 공간에 올라간다.

06예약(reserve)만 하고 submit도 discard도 안 한 채 리턴해도 된다.

정답 X. verifier가 거부한다. 예약한 자원은 반드시 제출하거나 버려야 한다. 조건부로 버릴 때 쓰는 게 bpf_ringbuf_discard()다.

07bpf_get_current_pid_tgid()의 하위 32비트가 커널 관점의 PID(스레드 ID)다.

정답 O. 상위 32비트가 TGID(= 유저가 말하는 PID), 하위 32비트가 커널의 PID = TID다. 직관과 반대라 한 번은 꼭 헷갈린다.

08comm이 16바이트인 것은 이 예제가 임의로 정한 크기다.

정답 X. 커널 task_struct.comm의 크기 그대로다(TASK_COMM_LEN). 리눅스 프로세스 이름이 15자 + NUL로 잘리는 이유가 이것이다.

09name->name으로 직접 읽으나 BPF_CORE_READ(name, name)으로 읽으나 결과는 같다.

정답 X. 직접 접근은 빌드 당시 오프셋이 그대로 박힌다. BPF_CORE_READ는 재배치 정보를 남겨서, 로드 시점에 현재 커널 BTF를 보고 오프셋이 교정된다.

10do_unlinkat에서 경로를 읽을 때는 bpf_probe_read_kernel_str()이 맞다.

정답 O. 이 시점엔 경로가 이미 커널로 복사된 뒤다. _user를 쓰면 에러 없이 빈 문자열이 나와서 원인 찾기가 더 어렵다.

11kprobe는 fentry보다 오버헤드가 작다.

정답 X. 반대다. kprobe는 트랩 → 예외 처리 경로를 탄다. fentry는 함수 진입부에 BPF 트램폴린을 직접 심어서 그 비용이 없다(03번).

12커널 함수의 인자 타입이 바뀌면 kprobe 코드는 컴파일 단계에서 에러가 난다.

정답 X. 컴파일은 그대로 된다. 대신 런타임에 엉뚱한 메모리를 읽는다. 이 조용한 실패가 kprobe의 가장 위험한 성질이고, fentry가 푸는 문제다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1링버퍼에서 이벤트 공간을 예약하는 헬퍼는?
e = ______(&events, sizeof(*e), 0); 
e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
if (!e)
        return 0;

실패하면 NULL이 온다. 바로 뒤의 NULL 체크는 verifier가 요구하는 필수 코드다.

C2예약해 둔 이벤트를 버릴 때 쓰는 헬퍼는?
______(e, 0); return 0; 
bpf_ringbuf_discard(e, 0);

Lv4 필터에서 쓴다. submit 하면 유저 공간으로 가고, discard 하면 조용히 사라진다. 둘 중 하나는 반드시 불러야 한다.

C3커널 심볼이 실제로 존재하는지 확인하는 명령은? 
grep ' [tT] do_unlinkat$' /proc/kallsyms

부착 실패의 첫 번째 원인이 심볼 부재다. kprobe를 쓸 때는 코드 작성 전에 항상 이걸 먼저 확인한다.
