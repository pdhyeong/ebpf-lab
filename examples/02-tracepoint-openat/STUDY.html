00eBPF 자체를 먼저

예제로 들어가기 전에, eBPF가 무슨 물건인지부터 정리한다. 이 절만 이해하면 01~14번이 전부 같은 이야기의 변주로 보인다.

한 문장

커널을 다시 컴파일하지도, 모듈을 올리지도 않고,
커널 안에서 내 코드를 안전하게 실행하는 장치.

왜 이런 게 생겼나

커널 동작을 바꾸거나 들여다보려면 원래 커널 모듈을 짜야 했다. 모듈은 커널과 같은 주소 공간에서 아무 제약 없이 돌기 때문에, 포인터 하나 잘못 만지면 시스템 전체가 죽는다. 프로덕션 서버에 함부로 넣을 물건이 아니다.

eBPF는 그 문제를 “실행 전에 증명하게 만드는” 방식으로 풀었다. 코드를 커널에 넣기 전에 verifier가 모든 실행 경로를 시뮬레이션해서 “이 프로그램은 반드시 끝나고, 잘못된 메모리를 건드리지 않는다”를 확인한다. 통과 못 하면 아예 로드가 안 된다. 그래서 커널을 죽일 수가 없다.

커널 모듈

  • 제약 없음 — 뭐든 할 수 있다
  • 버그 = 커널 패닉
  • 커널 버전마다 다시 빌드
  • 로드하면 되돌리기 어렵다

eBPF

  • 제약 많음 — verifier가 통과시킨 것만
  • 버그 = 로드 실패 (시스템은 멀쩡)
  • CO-RE로 한 번 빌드해 여러 커널에서
  • fd 닫으면 즉시 사라진다

실행 모델 — 스스로 돌지 않는다

eBPF 프로그램은 main()이 없다. 이벤트가 발생할 때만 호출되는 콜백 함수 하나라고 보면 된다. 그래서 두 가지가 반드시 필요하다:

  • 훅(hook) — 어떤 사건에 반응할지. 붙이지 않으면 로드돼 있어도 절대 실행되지 않는다.
  • 맵(map) — 결과를 밖으로 내보내는 통로. printf가 없으니 맵이 유일한 출구다.

CO-RE와 BTF — 한 번 빌드해서 여러 커널에서

커널 구조체 필드의 오프셋은 커널 빌드마다 다르다. struct sock의 skc_daddr이 이 커널에선 +40, 저 커널에선 +48일 수 있다. 옛날에는 대상 서버에서 커널 헤더를 받아 그때그때 컴파일했다(BCC 방식 — 서버마다 clang이 필요했다).

CO-RE(Compile Once, Run Everywhere)는 이렇게 푼다:

  1. 커널이 자기 타입 정보를 BTF로 노출한다 → /sys/kernel/btf/vmlinux
  2. bpftool로 그걸 C 헤더로 뽑는다 → make vmlinux → include/vmlinux.h
  3. BPF_CORE_READ()로 필드를 읽으면 컴파일러가 “재배치 정보”를 남긴다
  4. 로드할 때 로더가 현재 커널의 BTF를 보고 오프셋을 고쳐 넣는다
/* 나쁨: 빌드 당시 오프셋이 그대로 박힌다 */
__u32 daddr = sk->__sk_common.skc_daddr;

/* 좋음: CO-RE 재배치가 걸린다 */
__u32 daddr = BPF_CORE_READ(sk, __sk_common.skc_daddr);

eBPF가 못 하는 것

과대평가를 막기 위해 한계도 같이 알아두는 게 좋다.

  • 임의의 커널 코드 실행 — 헬퍼로 허가된 것만. 커널 API를 마음대로 부를 수 없다.
  • 긴 계산·복잡한 자료구조 — 명령어 상한과 루프 제약 때문에. 무거운 건 유저 공간에서.
  • 블로킹 — 잠들 수 없다(일부 sleepable 프로그램 타입 예외). 락을 잡고 기다릴 수 없다.
  • 부동소수점 — 없다.
  • 완전한 은닉 — bpftool prog list에 다 보인다. 루트 권한이 필요하고, 흔적이 남는다.

감각의 차이

03tracepoint의 정체

“커널이 공식 선언한 지점”이라는 말이 실제로 무슨 뜻인지 — 커널 소스와 tracefs 파일로 확인한다.

커널 소스에 이미 박혀 있는 구멍이다

tracepoint는 커널 코드 안에 미리 심어둔 호출 지점이다. 시스템콜 진입부에는 trace_sys_enter(regs, nr) 같은 호출이 이미 들어 있고, 평소에는 그 자리가 NOP으로 패치돼 있어 비용이 사실상 0이다. 누군가 이 tracepoint를 켜면 커널이 그 NOP을 실제 점프로 바꿔치기한다(static key / jump label).

즉 kprobe처럼 런타임에 브레이크포인트 명령을 박아 넣는 게 아니라, 이미 뚫려 있던 구멍의 뚜껑을 여는 것에 가깝다. 이 차이가 세 가지 결과를 만든다.

  • 안 깨진다. tracepoint의 이름과 인자 목록은 커널이 ABI로 취급한다. 함부로 바꾸지 않는다.
  • 아키텍처 독립이다. kprobe로 openat을 잡으려면 arm64에서는 __arm64_sys_openat, x86_64에서는 __x64_sys_openat을 찾아야 한다. tracepoint 이름은 어디서나 sys_enter_openat이다.
  • 인자 레이아웃이 문서로 나와 있다. 아래 format 파일.

format 파일이 곧 계약서다

붙이는 순간 실제로 일어나는 일

Go 코드의 link.Tracepoint("syscalls", "sys_enter_openat", prog, nil) 한 줄은 cilium/ebpf 안에서 이렇게 풀린다 (v0.22.0 link/tracepoint.go):

  1. tracefs.EventID("syscalls", "sys_enter_openat") → 위에서 본 566을 .../id 파일에서 읽는다
  2. perf_event_open(type=PERF_TYPE_TRACEPOINT, config=566) → fd 획득
  3. 그 fd에 ioctl(PERF_EVENT_IOC_SET_BPF, prog_fd) → 프로그램 연결
  4. 거기에 PERF_EVENT_IOC_ENABLE → 이제 openat마다 내 코드가 돈다

반환된 Link는 그 fd를 들고 있다. fd가 닫히면 자동으로 detach 된다 — Go 프로세스가 죽으면 훅도 같이 사라진다는 뜻이고, defer tp.Close()가 그래서 있다. (프로세스가 죽어도 살려두려면 pinning이 필요한데, 그건 07번 예제에서 다룬다.)

04openat.bpf.c 한 줄씩

커널에서 돌 코드. 전부 합쳐 40줄인데 배울 게 여덟 개쯤 들어 있다.

  1. 맨 윗줄 — 이건 Go 파일이 아니다

    //go:build ignore

    이 .c 파일은 go build가 절대 건드리면 안 된다. clang이 BPF 타깃으로 따로 컴파일할 파일이기 때문이다. Go 빌드 태그로 “나를 무시해라”라고 표시해 둔 것.

  2. 헤더 세 개

    #include "vmlinux.h"            /* 커널 BTF에서 뽑은 전체 타입 정의 (15만 줄) */
#include <bpf/bpf_helpers.h>    /* SEC(), bpf_map_lookup_elem() 등 헬퍼 선언 */
#include <bpf/bpf_core_read.h>  /* BPF_CORE_READ — 02번에선 안 쓴다 */
#include <bpf/bpf_tracing.h>    /* BPF_KPROBE 매크로 등 — 02번에선 안 쓴다 */

    vmlinux.h는 make vmlinux가 bpftool btf dump file /sys/kernel/btf/vmlinux format c로 만든 파일이다. 커널 헤더를 설치할 필요가 없는 이유가 이것 — 지금 돌고 있는 커널이 자기 타입 정보를 BTF로 노출하고, 그걸 그대로 C 헤더로 뽑아 쓴다.

    뒤의 두 헤더는 01번에서 복사해 온 흔적이다. 지워도 02번은 컴파일된다 — 직접 지워보는 것도 좋은 연습.

  3. 라이선스 선언은 장식이 아니다

    char __license[] SEC("license") = "Dual MIT/GPL";

    SEC("license")는 ELF에 license라는 섹션을 만든다. 커널은 로드할 때 이 값을 본다. GPL 호환이 아니면 GPL-only 헬퍼를 못 쓴다 — bpf_probe_read_kernel(), bpf_get_current_comm() 같은 핵심 헬퍼가 여기 해당한다. 이 줄을 빼면 로드 단계에서 거부당한다.

  4. 맵의 키가 될 구조체

    #define TASK_COMM_LEN 16

struct proc_key {
	__u32 tgid;                /* 4바이트 */
	__u8 comm[TASK_COMM_LEN];  /* 16바이트 */
};                             /* 합계 20바이트, 패딩 없음 */

struct proc_key *unused_proc_key __attribute__((unused));

    마지막 줄이 이상해 보일 텐데, 어디에도 쓰이지 않는 전역 포인터를 일부러 선언한 것이다. 이유: bpf2go에 -type proc_key를 주면 이 구조체를 Go 구조체로 뽑아주는데, 그러려면 그 타입이 컴파일 결과물의 BTF에 남아 있어야 한다. C 컴파일러는 “아무도 안 쓰는 타입”을 그냥 버린다. 그래서 억지로 한 번 참조시킨다. (커널에 로드되는 실제 명령어에는 아무 영향이 없다.)

    TASK_COMM_LEN 16은 커널의 task_struct.comm 크기 그대로다. 리눅스 프로세스 이름이 15자 + NUL로 잘리는 이유가 여기 있다.

  5. 맵 두 개 — 문법이 낯설지만 규칙적이다

    struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__type(key, struct proc_key);
	__type(value, __u64);
	__uint(max_entries, 8192);
} counts SEC(".maps");

struct {
	__uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
	__type(key, __u32);
	__type(value, __u64);
	__uint(max_entries, 1);
} total SEC(".maps");

    진짜 구조체가 아니라 메타데이터를 표현하는 관용구다. __uint/__type은 0 크기 배열 트릭으로 “이 맵은 이런 타입”이라는 정보를 BTF에 심는 매크로고, 로더(cilium/ebpf)가 그걸 읽어서 실제 맵을 만든다. 외울 건 type / key / value / max_entries 네 줄뿐이다.

    counts HASH

    “프로세스별로 몇 번”을 센다. 키가 (tgid, comm)이므로 프로세스마다 항목이 하나씩 생긴다.

    max_entries 8192 = 동시에 추적 가능한 프로세스 수 상한. 넘치면 새 항목 삽입이 E2BIG로 실패한다(조용히 카운트를 잃는다).

    total PERCPU_ARRAY

    “전체 몇 번”만 센다. 키는 인덱스 0 하나뿐.

    PERCPU = CPU마다 별도 복사본이 존재한다. 그래서 락도 원자 연산도 필요 없다. 대신 읽을 때 CPU 개수만큼 합산해야 한다.

  6. SEC 이름이 부착 지점을 결정한다

    SEC("tracepoint/syscalls/sys_enter_openat")
int handle_openat(struct trace_event_raw_sys_enter *ctx)

    이 문자열은 주석이 아니라 ELF 섹션 이름이고, 로더가 이걸 파싱해서 “프로그램 타입 = BPF_PROG_TYPE_TRACEPOINT, 붙을 곳 = syscalls/sys_enter_openat”을 알아낸다. ctx 타입도 이 프로그램 타입에 따라 정해진다 — kprobe면 struct pt_regs *, tracepoint면 위에서 본 struct trace_event_raw_sys_enter *다.

    반환값 int는 tracepoint에서는 의미가 없다(그냥 0을 리턴한다). XDP나 LSM 같은 타입에서는 이 반환값이 “통과/드롭/차단”을 결정한다 — 05·10번에서 만난다.

  7. 본문 전반 — 키 만들기

    struct proc_key key = {};   /* ← 이 = {} 가 중요하다 */
__u64 init = 1, *cnt;

key.tgid = bpf_get_current_pid_tgid() >> 32;
bpf_get_current_comm(&key.comm, sizeof(key.comm));

    bpf_get_current_pid_tgid()는 __u64 하나에 두 값을 담아 준다:

    • 상위 32비트 = TGID — 유저가 “PID”라고 부르는 그것 (프로세스)
    • 하위 32비트 = PID — 커널이 말하는 PID, 즉 스레드 ID

    헷갈리기 딱 좋은 지점이다. 프로세스 단위로 세고 싶으니 >> 32로 TGID만 쓴다. 01번 예제는 둘 다 뽑아서 PID/TID 컬럼으로 보여준다.

  8. 본문 후반 — 두 가지 카운팅 방식이 나란히 있다

    cnt = bpf_map_lookup_elem(&counts, &key);
if (cnt)
	__sync_fetch_and_add(cnt, 1);      /* 방식 A: 원자적 증가 */
else
	bpf_map_update_elem(&counts, &key, &init, BPF_ANY);

__u32 zero = 0;
cnt = bpf_map_lookup_elem(&total, &zero);
if (cnt)
	(*cnt)++;                          /* 방식 B: 그냥 증가 */

return 0;

    같은 “+1”인데 왜 다르게 쓰는지가 이 예제의 핵심 학습 포인트다.

    A. HASH → 원자 연산 필요

    일반 HASH 맵의 값은 모든 CPU가 공유하는 메모리 한 덩어리다. CPU 0과 CPU 3이 동시에 (*cnt)++를 하면 읽기→더하기→쓰기가 겹쳐서 하나를 잃는다. __sync_fetch_and_add는 BPF 바이트코드의 lock add 명령으로 컴파일된다.

    B. PERCPU → 원자 연산 불필요

    bpf_map_lookup_elem이 지금 이 CPU의 복사본 주소를 돌려준다. 다른 CPU는 다른 주소를 본다. 경쟁 자체가 없으므로 평범한 ++가 더 빠르고 안전하다.

    그리고 if (cnt) — 이 NULL 체크는 선택이 아니다. bpf_map_lookup_elem의 반환 타입은 verifier 입장에서 “NULL일 수도 있는 포인터”이고, 체크 없이 역참조하면 로드가 거부된다: R0 invalid mem access 'map_value_or_null'

함정 · 이 코드에 남아 있는 진짜 버그

lookup 했는데 없어서 update_elem(..., 1)로 새로 넣는 경로에는 경쟁 조건이 있다. CPU 두 개가 동시에 “없네?”를 확인하면 둘 다 값을 1로 덮어써서 카운트 하나를 잃는다. 새 프로세스가 처음 등장하는 순간에만 발생하므로 실습에서는 티가 안 나지만, 실무에서는 진짜 문제다.

고치는 법 세 가지 — 직접 시도해 볼 것:

  • BPF_NOEXIST로 삽입 → EEXIST면 다시 lookup 해서 원자 증가
  • BPF_MAP_TYPE_PERCPU_HASH로 바꾸기 (읽을 때 합산해야 함)
  • bpf_map_lookup_or_try_init() 패턴 (libbpf-tools가 쓰는 관용구)
패딩 이야기 — = {}를 빼면 안 되는 이유

해시 맵의 키 비교는 바이트 단위 memcmp다. 구조체에 패딩 바이트가 있는데 그게 초기화 안 된 스택 쓰레기값이면, 논리적으로 같은 키인데 다른 항목으로 들어간다. 지금 struct proc_key는 u32 + u8[16] = 20바이트로 패딩이 없어서 운 좋게 안전하지만, 여기에 __u64 uid 같은 걸 넣는 순간 정렬 때문에 패딩이 생긴다. struct proc_key key = {};는 그 대비책이다. 맵 키 구조체는 항상 0으로 초기화한다 — 관용 규칙으로 외워라.

Frida는 send({pid: 1, comm: "nginx"})처럼 아무 객체나 던지면 JSON으로 넘어온다. eBPF는 커널과 유저가 같은 바이트 레이아웃에 합의해야 한다. bpf2go -type은 그 합의를 C 구조체 하나에서 자동으로 만들어 주는 장치다. C 쪽 구조체를 고치면 Go 구조체도 자동으로 따라온다 — 그래서 make generate를 잊으면 조용히 깨진다.

main() 흐름

  1. memlock 제한 풀기

    rlimit.RemoveMemlock()

    5.11 이전 커널은 BPF 맵 메모리를 RLIMIT_MEMLOCK으로 제한했고, 기본값이 작아서 맵 생성이 자주 실패했다. 5.11+ 는 cgroup 메모리로 계산하므로 이 줄은 사실상 no-op이지만, 관용적으로 넣는다.

  2. 로드 — 여기서 verifier를 만난다

    var objs openatObjects
if err := loadOpenatObjects(&objs, nil); err != nil { ... }
defer objs.Close()

    이 한 줄 안에서 벌어지는 일:

    • embed된 .o를 파싱해서 맵 정의와 프로그램을 꺼낸다
    • bpf(BPF_MAP_CREATE)로 counts, total 맵을 먼저 만든다
    • 바이트코드 안의 “맵 참조” 자리에 방금 만든 맵 fd를 박아 넣는다 (relocation)
    • bpf(BPF_PROG_LOAD) → verifier 검증 → 통과하면 JIT

    verifier 에러는 여기서 나온다. 에러 메시지가 수백 줄이라도 맨 마지막 몇 줄이 진짜 원인이다.

  3. 부착

    tp, err := link.Tracepoint("syscalls", "sys_enter_openat", objs.HandleOpenat, nil)
defer tp.Close()

    03절에서 본 perf_event_open + ioctl 조합이 이 안에서 일어난다. objs.HandleOpenat은 SEC()의 함수 이름 handle_openat이 Go 관례로 바뀐 것.

    로드와 부착은 별개다. 로드만 하고 부착 안 하면 프로그램은 커널에 존재하지만 절대 실행되지 않는다.

  4. 1초 폴링 루프

    tick := time.NewTicker(time.Second)
for {
	select {
	case <-stop:  return
	case <-tick.C:
		rows, _ := snapshot(&objs)
		total, _ := readTotal(&objs)
		// 출력
	}
}

    01번의 rd.Read() 블로킹 루프와 대비된다. 커널이 밀어주는 게 아니라 내가 당겨온다. 주기를 5초로 늘려도 데이터를 잃지 않는다 — 커널이 계속 누적하고 있으니까.

  5. 맵 전체 순회

    iter := objs.Counts.Iterate()
for iter.Next(&key, &val) {
	rows = append(rows, row{tgid: key.Tgid, comm: cstr(key.Comm[:]), count: val})
}
sort.Slice(rows, func(i, j int) bool { return rows[i].count > rows[j].count })

    내부적으로 BPF_MAP_GET_NEXT_KEY + BPF_MAP_LOOKUP_ELEM을 반복한다. 원자적 스냅샷이 아니다 — 순회하는 동안에도 커널은 계속 값을 올린다. 통계 용도라 문제없지만, “정확히 이 순간의 합”이 필요하면 다른 설계가 필요하다.

    정렬이 유저 공간에서 일어난다는 점에 주목. BPF 프로그램은 정렬 같은 걸 할 수 없다(루프 제약). 커널은 모으고, 유저가 가공한다 — eBPF 도구의 일반적인 역할 분담이다.

  6. PERCPU 맵 읽기 — 여기서 한 번은 꼭 헷갈린다

    var perCPU []uint64
objs.Total.Lookup(uint32(0), &perCPU)   // ← 슬라이스로 받는다!
var sum uint64
for _, v := range perCPU { sum += v }

    키가 0 하나뿐인데도 값이 슬라이스로 온다. 이 랩의 커널은 CPU가 10개이므로 len(perCPU) == 10이고, 직접 더해야 진짜 총합이 나온다. var v uint64로 받으면 런타임 에러가 난다.

    PERCPU 맵의 거래 조건: 쓰기가 빨라지는 대신(락 없음) 읽기가 번거로워진다(합산 필요).

08과제와 함정

읽기만 하면 안 는다. 아래 순서대로 하면 난이도가 한 칸씩 올라간다.

LV 1유저 공간만 고치기

상위 10개 → 20개로, 정렬을 카운트순 → PID순으로 바꾼다. main.go의 snapshot()과 출력부만 건드린다.

얻는 것: make generate가 필요 없는 변경이 있다는 감각. 커널 코드와 유저 코드의 경계선이 어디인지 몸으로 안다.

LV 1.5누적값을 초당 비율로

직전 스냅샷을 map[uint32]uint64에 저장해 두고 차이를 출력한다. BPF 코드는 그대로다.

생각할 것: 이 계산을 커널에서 하면 안 되나? — 하려면 “직전 값”과 “시각”을 맵에 더 넣어야 하고, 커널 코드는 복잡해지는데 얻는 게 없다. 어디까지 커널에서 하고 어디부터 유저에서 할지가 실무 설계의 핵심 판단이다.

LV 2키에 UID 추가

struct proc_key에 __u32 uid를 넣고 bpf_get_current_uid_gid() & 0xFFFFFFFF로 채운다. make generate → Go 구조체가 자동으로 따라오는지 확인.

  • 확인: bpftool map list의 key 20B가 24B로 바뀐다.
  • 함정: 필드를 __u64로 넣으면 정렬 때문에 패딩이 생긴다. = {} 초기화가 왜 필수인지 여기서 실감할 수 있다.
  • 생각할 것: 키가 커지면 max_entries 8192의 메모리 비용도 커진다(위 memlock 숫자).
LV 3실패한 openat만 세기

tracepoint/syscalls/sys_exit_openat을 하나 더 붙여서 ctx->ret < 0인 것만 별도 카운터에 넣는다.

SEC("tracepoint/syscalls/sys_exit_openat")
int handle_openat_exit(struct trace_event_raw_sys_exit *ctx)
{
	if (ctx->ret >= 0)
		return 0;
	/* ... 실패 카운터 증가 ... */
}

Go 쪽에서는 link.Tracepoint("syscalls", "sys_exit_openat", objs.HandleOpenatExit, nil)을 추가로 호출하고 그 Link도 defer Close().

핵심 질문: 진입과 종료를 짝지어야 하나? — “실패 횟수만” 세는 거라면 필요 없다(exit만 봐도 충분). 하지만 “어떤 파일을 열려다 실패했나”를 알고 싶으면 enter에서 PID를 키로 파일명을 저장하고 exit에서 꺼내야 한다. 이 패턴(enter에 저장 → exit에 회수)이 지연시간 측정의 기본 골격이다. 03번의 fentry/fexit가 이걸 훨씬 깔끔하게 해준다.

LV 4파일명까지 읽기 — 유저 포인터의 벽

가장 많이 배우는 과제다. args[1]의 문자열을 실제로 읽어서 “가장 많이 열린 파일 top 10”을 만든다.

struct file_key { __u8 path[64]; };

const char *fname = (const char *)ctx->args[1];   /* ← args[0] 아니다! */
struct file_key fk = {};
bpf_probe_read_user_str(&fk.path, sizeof(fk.path), fname);
  • *fname으로 바로 못 읽는다. verifier가 거부한다. 이유: 유저 공간 메모리는 언제든 페이지 폴트 날 수 있고, 다른 프로세스가 그 사이에 바꿀 수도 있다(TOCTOU).
  • _kernel이 아니라 _user다. 01번의 bpf_probe_read_kernel_str은 struct filename이 이미 커널 안으로 복사된 뒤라서 그렇다. 여기는 시스템콜 진입 직후라 포인터가 아직 유저 공간을 가리킨다. 잘못 쓰면 조용히 빈 문자열이 나온다.
  • 스택 512B 제약. path[256]쯤 잡으면 다른 지역 변수와 합쳐 한도를 넘길 수 있다. 크게 잡아야 하면 PERCPU_ARRAY를 스크래치 버퍼로 쓰는 게 관용구다.
  • 맵이 폭발한다. 파일 경로는 종류가 프로세스보다 훨씬 많다. max_entries를 늘리거나 BPF_MAP_TYPE_LRU_HASH로 바꿔야 한다 — LRU가 왜 존재하는지를 여기서 배운다.

verifier에게 거부당했을 때

과제를 하다 보면 반드시 만난다. 순서대로 하면 대부분 풀린다.

  1. 에러의 마지막 5줄만 본다. 앞의 수백 줄은 명령어 추적 로그다. 마지막에 R1 type=... expected=... 같은 진짜 원인이 있다.
  2. NULL 체크를 빠뜨렸는지 본다. map_value_or_null이 보이면 if (ptr)가 없는 것이다.
  3. 포인터를 직접 읽었는지 본다. bpf_probe_read_user/kernel을 거쳐야 하는 자리가 아닌지.
  4. 스택을 넘겼는지 본다. combined stack size exceeds 512.
  5. bpf_printk("here %d\n", x)를 박고 cat /sys/kernel/debug/tracing/trace_pipe로 확인한다 — eBPF의 console.log다. 느리므로 디버깅 후엔 지운다.

다음으로 넘어가기 전 자가 점검

아래에 막힘없이 답할 수 있으면 03번(fentry/fexit)으로 가도 된다.

  • kprobe 대신 tracepoint를 쓰면 뭐가 좋아지나? 대신 뭘 포기하나? (포기: 아무 함수에나 못 붙는다 — 커널이 뚫어둔 곳만)
  • ringbuf와 hash 집계 중 뭘 쓸지 어떻게 정하나?
  • HASH 값은 __sync_fetch_and_add인데 PERCPU 값은 그냥 ++인 이유는?
  • PERCPU 맵을 유저 공간에서 읽으면 왜 슬라이스가 오나?
  • ctx->args[1]이 가리키는 문자열을 그냥 못 읽는 이유는?
  • Go 프로세스를 죽이면 커널의 프로그램과 맵은 어떻게 되나?
  • struct proc_key key = {};의 = {}를 빼면 뭐가 잘못될 수 있나?

03번이 이어서 푸는 문제

02번의 한계는 tracepoint가 없는 곳에는 못 붙는다는 것이다. tcp_connect() 같은 커널 내부 함수에는 tracepoint가 없다. 01번의 kprobe로 붙을 수는 있지만 타입 안전성이 없다. fentry/fexit는 BTF를 이용해 “아무 함수에나 붙되, 시그니처가 틀리면 로드 시점에 거부되는” 제3의 길을 준다 — kprobe의 자유도와 tracepoint의 안전성을 동시에 갖는다. Cilium과 Tetragon이 실제로 쓰는 방식이다.

09퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

점수 0 / 20 아직 안 풀었다

A. eBPF 기초 (00절)

01eBPF 프로그램은 버그가 있으면 커널 패닉을 낼 수 있다.

정답 X. verifier가 로드 시점에 모든 실행 경로를 검증해서, 위험한 코드는 애초에 커널에 들어가지 못한다. 버그의 결과는 패닉이 아니라 로드 실패다. 이게 커널 모듈과의 결정적 차이다.

02프로그램을 커널에 로드하면 바로 실행되기 시작한다.

정답 X. 로드와 부착(attach)은 별개다. 훅에 붙이지 않으면 커널에 존재하기만 하고 절대 호출되지 않는다. eBPF 프로그램은 main()이 없는 이벤트 콜백이다.

03BPF 바이트코드는 커널에서 인터프리터로 해석 실행된다.

정답 X. 검증을 통과하면 JIT가 네이티브 기계어로 컴파일한다. bpftool prog list의 jited 416B가 그 증거다. (인터프리터 폴백은 JIT 미지원 아키텍처에만 해당.)

04eBPF 프로그램 안에서는 원칙적으로 무한 루프를 쓸 수 없다.

정답 O. 커널 안에서 끝나지 않으면 시스템이 멈춘다. verifier는 반드시 종료됨을 증명할 수 있어야 통과시킨다. 5.3+ 부터 상한이 증명되는 유한 루프는 허용된다.

05BPF 프로그램은 필요한 커널 함수를 자유롭게 호출할 수 있다.

정답 X. 커널이 번호를 매겨 허가한 헬퍼 함수만 부를 수 있다. 바이트코드의 call 0x1이 함수 주소가 아니라 헬퍼 번호(bpf_map_lookup_elem)인 이유다.

06BPF 프로그램의 스택은 512바이트로 제한된다.

정답 O. 커널 스택 자체가 작기 때문이다(보통 8~16KB). 큰 버퍼가 필요하면 PERCPU_ARRAY 맵을 스크래치 공간으로 쓰는 게 관용구다.

07vmlinux.h를 쓰려면 대상 머신에 커널 헤더 패키지가 설치돼 있어야 한다.

정답 X. 정반대다. 커널이 BTF(/sys/kernel/btf/vmlinux)로 자기 타입 정보를 노출하고, bpftool btf dump ... format c로 헤더를 뽑는다. 커널 헤더 설치가 필요 없어진 게 CO-RE의 핵심 이득이다.

08eBPF는 관찰(observability) 전용이고 동작을 차단할 수는 없다.

정답 X. 프로그램 타입에 따라 반환값이 결정을 바꾼다. XDP는 XDP_DROP으로 패킷을 버리고, LSM 훅은 -EPERM을 반환해 실행 자체를 막는다. (이 랩의 10·11·13번이 그것.)

09tracepoint는 kprobe보다 커널 버전 변화에 강하다.

정답 O. tracepoint의 이름과 인자 목록은 커널이 ABI로 취급한다. kprobe는 내부 함수 주소에 붙으므로 시그니처가 바뀌면 컴파일은 되는데 엉뚱한 메모리를 읽는다.

10Go 프로세스가 종료되면 부착했던 훅도 함께 해제된다.

정답 O. Link는 fd를 들고 있고, fd가 닫히면 커널 객체가 회수된다. 프로세스가 죽어도 남기려면 pinning(/sys/fs/bpf)이 필요하다 — 07번 주제.

B. 02번 예제 (03~06절)

11sys_enter_openat에서 파일명 포인터는 ctx->args[0]이다.

정답 X. args[0]은 dfd, args[1]이 filename이다. format 파일이 오프셋 16=dfd, 24=filename이라고 알려준다. args[0]이 파일명인 건 인자 3개짜리 옛 open(2) 쪽이다.

12tracepoint 이름은 아키텍처마다 달라서 arm64/x86을 따로 처리해야 한다.

정답 X. 그건 kprobe 얘기다(__arm64_sys_openat vs __x64_sys_openat). tracepoint 이름은 어디서나 sys_enter_openat이다 — 시스템콜을 잡을 때 tracepoint를 쓰는 큰 이유 중 하나.

13bpf_get_current_pid_tgid()의 상위 32비트가 유저 공간에서 말하는 PID다.

정답 O. 상위 32비트 = TGID = 우리가 PID라 부르는 것(프로세스). 하위 32비트 = 커널의 PID = 스레드 ID. 그래서 코드가 >> 32를 한다.

14일반 HASH 맵의 값을 증가시킬 때는 원자 연산이 필요하다.

정답 O. HASH 맵의 값은 모든 CPU가 공유하는 메모리 한 덩어리다. 여러 CPU가 동시에 (*cnt)++하면 읽기→더하기→쓰기가 겹쳐 카운트를 잃는다. __sync_fetch_and_add가 lock add 명령으로 컴파일된다.

15PERCPU 맵의 값을 증가시킬 때도 원자 연산을 써야 안전하다.

정답 X. bpf_map_lookup_elem이 지금 이 CPU의 복사본 주소를 돌려주므로 경쟁 자체가 없다. 평범한 (*cnt)++가 더 빠르고 안전하다. 02번 코드에 두 방식이 나란히 있는 이유다.

16PERCPU 맵을 유저 공간에서 Lookup하면 값 하나가 돌아온다.

정답 X. CPU 개수만큼의 슬라이스가 온다(이 랩은 10개). 직접 합산해야 진짜 총합이 나온다. var v uint64로 받으면 런타임 에러다. 쓰기가 빨라진 대가를 읽기에서 치르는 구조.

17bpf_map_lookup_elem()의 반환 포인터는 바로 역참조해도 된다.

정답 X. verifier가 이 반환값을 map_value_or_null로 추적한다. NULL 체크 없이 쓰면 R0 invalid mem access로 로드가 거부된다. 바이트코드의 if r0 == 0x0 goto가 그 체크다.

18ctx->args[1]이 가리키는 문자열은 bpf_probe_read_kernel_str()로 읽는다.

정답 X. 시스템콜 진입 직후라 포인터가 아직 유저 공간을 가리킨다. bpf_probe_read_user_str()을 써야 한다. _kernel을 쓰면 에러도 안 나고 조용히 빈 문자열이 나와서 더 골치 아프다.

19SEC("license")에 GPL 호환 라이선스가 없으면 일부 헬퍼를 쓸 수 없다.

정답 O. bpf_probe_read_kernel(), bpf_get_current_comm() 같은 핵심 헬퍼가 GPL-only다. 커널이 로드 시점에 license 섹션을 확인하고 거부한다.

20맵을 순회(Iterate)하는 동안 값은 고정되어 원자적 스냅샷을 얻는다.

정답 X. GET_NEXT_KEY + LOOKUP을 반복할 뿐이라 순회 중에도 커널은 계속 값을 올린다. 통계 용도라 문제없지만, "정확히 이 순간의 합"이 필요하면 다른 설계가 필요하다.

______(&key.comm, sizeof(key.comm)); 
bpf_get_current_comm(&key.comm, sizeof(key.comm));

C2공유 HASH 맵 카운터를 안전하게 1 증가시키려면?
______(cnt, 1); 
__sync_fetch_and_add(cnt, 1);

BPF 바이트코드의 lock *(u64 *)(r0 + 0x0) += r6으로 컴파일된다. PERCPU 맵이었다면 그냥 (*cnt)++로 충분하다.
