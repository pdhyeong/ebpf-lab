ebpf-lab/예제 03/fentry / fexit

타입을 아는 훅

kprobe는 아무 데나 붙지만 아무것도 보장하지 않았다. tracepoint는 안전하지만 커널이 뚫어둔 곳에만 붙는다. fentry/fexit는 그 둘 사이를 뚫는다 — 아무 함수에나 붙되, 시그니처가 틀리면 로드 시점에 거부된다. Cilium과 Tetragon이 실제로 쓰는 방식이다.

00fentry/fexit란 무엇인가

BTF + 트램폴린. kprobe의 자유도와 tracepoint의 안전성을 동시에 갖는다.

트램폴린 — 트랩이 아니다

kprobe는 명령어를 트랩으로 덮어써서 예외 처리 경로를 탄다. 비싸다. fentry는 컴파일러가 모든 커널 함수 진입부에 미리 넣어 둔 nop 자리(ftrace)를 직접 점프로 바꿔치기한다. 그 점프가 향하는 곳이 BPF 트램폴린 — 커널이 내 프로그램만을 위해 생성한 작은 어셈블리 조각이다.

결과적으로 함수 호출 한 번 수준의 비용밖에 안 든다. 그래서 실무 에이전트가 kprobe를 버리고 여기로 옮겼다.

kprobefentry
방식명령어를 트랩으로 교체ftrace nop → 트램폴린 점프
비용예외 처리 경로 (비쌈)함수 호출 수준 (쌈)
인자struct pt_regs *에서 파낸다타입 그대로 받는다
시그니처 오류런타임에 조용히 오작동로드 시점 거부
반환값kretprobe 별도 + 맵으로 인자 전달fexit 하나로 인자+반환값
필요 조건심볼만 있으면 됨BTF + DIRECT_CALLS 커널 옵션

왜 타입을 알까 — BTF

커널이 /sys/kernel/btf/vmlinux에 자기 타입 정보를 통째로 노출한다. 거기에는 tcp_connect의 시그니처(int tcp_connect(struct sock *sk))도 들어 있다. 로드할 때 커널이 내가 선언한 인자와 BTF의 실제 시그니처를 대조한다. 틀리면 그 자리에서 거부한다 — kprobe에서 가장 위험했던 "조용한 오작동"이 사라지는 지점이다.

fexit이 kretprobe보다 나은 이유

kretprobe로 "이 sk에 대한 tcp_connect가 실패했다"를 알려면, 진입 시점에 PID를 키로 sk를 맵에 저장하고 반환 시점에 다시 꺼내야 한다. 맵도 하나 더 필요하고, 저장했는데 반환을 못 잡으면 누수가 생긴다.

fexit은 이 과정이 통째로 없다:

SEC("fexit/tcp_connect")
int BPF_PROG(tcp_connect_exit, struct sock *sk, int ret)
//                             ↑ 진입 인자      ↑ 반환값 — 한자리에 다 있다

01이 랩이 하는 일

tcp_connect에 진입/반환 양쪽으로 붙어서 TCP 연결 시도를 관측한다.

대상 — tcp_connect(struct sock *sk)

net/ipv4/tcp_output.c에 있다. TCP 3-way handshake의 SYN을 보내기 직전에 호출된다. 즉 "연결이 성립됐다"가 아니라 "연결을 시도했다"를 잡는 지점이다. 연결 거부(RST)든 타임아웃이든 시도 자체는 전부 여기를 지난다 — 관측 목적으로는 이게 더 유용하다.

struct sock에서 뭘 꺼내나

주소와 포트는 struct sock의 공통 헤더(struct sock_common)에 들어 있다. 바이트 오더가 필드마다 다른 게 함정이다:

필드내용바이트 오더
skc_familyAF_INET(2) / AF_INET6(10)—
skc_rcv_saddr로컬 IP네트워크
skc_daddr원격 IP네트워크
skc_num로컬 포트호스트 — 변환 불필요
skc_dport원격 포트네트워크 — bpf_ntohs 필요

skc_num만 호스트 오더인 게 커널의 오래된 관례다. 여기서 bpf_ntohs를 잘못 붙이거나 빼면 포트가 엉뚱한 큰 숫자로 나온다. 네트워크 eBPF에서 가장 흔한 버그다.

실행

make 03
# victim 컨테이너가 3초마다 HTTP 요청을 보내므로 가만히 둬도 이벤트가 찍힌다

# 직접 만들려면 — 거부돼도 tcp_connect 는 호출된다
make sh
bash -c 'exec 3<>/dev/tcp/127.0.0.1/59998'

make 03-check

02단계 공략

빈칸 4개. Lv3은 "안 보이는 것도 세라"가 주제다.

LV 1 · 30점호출 카운트 + 이벤트
bump(STAT_CALLS);
family = BPF_CORE_READ(sk, __sk_common.skc_family);
/* ... */
e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);

주목할 점: sk를 pt_regs에서 파내는 코드가 없다. BPF_PROG 매크로가 이미 struct sock * 타입으로 넘겨준다. kprobe였다면 PT_REGS_PARM1(ctx)로 뽑고 캐스팅해야 했다.

LV 2 · 25점CO-RE로 주소·포트 읽기
e->saddr = BPF_CORE_READ(sk, __sk_common.skc_rcv_saddr);
e->daddr = BPF_CORE_READ(sk, __sk_common.skc_daddr);
e->sport = BPF_CORE_READ(sk, __sk_common.skc_num);              // 호스트 오더
e->dport = bpf_ntohs(BPF_CORE_READ(sk, __sk_common.skc_dport)); // 네트워크 오더

채점 방법: 채점기가 127.0.0.1:59998로 연결을 시도하고, 출력에 그 포트가 정확히 찍히는지 본다. bpf_ntohs를 빼면 59998 대신 7914 같은 값이 나와서 바로 실패한다.

BPF_CORE_READ가 ->를 연쇄로 따라간다: sk->__sk_common.skc_daddr의 각 단계마다 재배치 정보를 남긴다. 직접 쓰면 오프셋이 박힌다.

LV 3 · 20점IPv6 분기 + fexit
/* fentry: IPv4 가 아니면 이벤트는 안 올리되, 있었다는 사실은 남긴다 */
if (family == AF_INET6)
        bump(STAT_IPV6);

/* fexit: 반환값으로 실패를 센다 */
if (ret != 0)
        bump(STAT_FAILED);

이 단계의 진짜 주제는 "안 보이는 것도 세라"다. IPv4만 화면에 찍고 IPv6를 그냥 버리면, 나중에 "왜 이 트래픽이 안 잡히지?"에 답할 수 없다. 필터로 버린 것의 개수를 남기는 것은 관측 시스템의 기본 예의다. 07번의 STAT_FILTERED·STAT_DROPPED가 같은 사상이다.

LV 4 · 10점커널 포트 필터 (보너스)

관심 없는 포트는 예약하기 전에 걸러라. 예약 후 discard보다 예약 전 return이 더 싸다. 이미 예약했다면 반드시 bpf_ringbuf_discard(e, 0)로 처리해야 verifier가 통과시킨다.

03함정과 확인

fentry는 환경 조건이 있다. 안 되면 여기부터 본다.

함정 1 · 로드가 거부된다

fentry는 시그니처가 틀리면 로드 자체가 안 된다. 이건 버그가 아니라 기능이다. 인자 개수·타입이 BTF의 실제 시그니처와 맞는지 먼저 확인하라:
bpftrace -l 'kfunc:*tcp_connect*' · bpftool btf dump file /sys/kernel/btf/vmlinux format c | grep -A2 'tcp_connect'

함정 2 · 커널이 fentry를 지원하지 않는다

두 가지가 필요하다 — CONFIG_DEBUG_INFO_BTF=y(BTF)와 CONFIG_DYNAMIC_FTRACE_WITH_DIRECT_CALLS=y(트램폴린). make check가 둘 다 확인한다. 이 랩의 커널은 둘 다 y다.

함정 3 · 포트가 이상한 숫자로 나온다

바이트 오더다. skc_dport는 네트워크 오더, skc_num은 호스트 오더. 59998(0xEA5E)을 뒤집으면 0x5EEA = 24298. 숫자가 "왠지 큰데 규칙적"이면 오더를 의심하라.

A. O / X

01fentry는 kprobe와 마찬가지로 대상 함수의 명령어를 트랩으로 덮어쓴다.

정답 X. fentry는 컴파일러가 미리 넣어둔 ftrace nop 자리를 트램폴린으로 향하는 점프로 바꾼다. 트랩/예외 경로를 타지 않아서 훨씬 싸다.

02fentry 프로그램의 인자 타입이 실제 커널 함수와 다르면 로드가 거부된다.

정답 O. BTF에 있는 실제 시그니처와 대조하기 때문이다. kprobe에서 가장 위험했던 "컴파일은 되는데 런타임에 엉뚱한 메모리를 읽는" 조용한 실패가 사라진다.

03fexit은 진입 인자와 반환값을 동시에 볼 수 있다.

정답 O. BPF_PROG(name, struct sock *sk, int ret)처럼 마지막 인자가 반환값이다. kretprobe라면 진입 시점에 맵으로 인자를 저장해 뒀다가 꺼내야 한다.

04fentry를 쓰려면 커널에 BTF가 있어야 한다.

정답 O. CONFIG_DEBUG_INFO_BTF=y가 필요하고, 트램폴린을 위해 CONFIG_DYNAMIC_FTRACE_WITH_DIRECT_CALLS=y도 필요하다. make check가 확인해 준다.

05tcp_connect는 TCP 연결이 성공적으로 성립된 뒤에 호출된다.

정답 X. 3-way handshake의 SYN을 보내기 직전이다. 거부되든 타임아웃이든 "시도" 자체가 전부 여기를 지나므로 관측 목적으로는 오히려 더 유용하다.

06skc_num(로컬 포트)은 네트워크 바이트 오더라서 bpf_ntohs가 필요하다.

정답 X. skc_num만 호스트 오더다. 변환하면 오히려 틀린다. 원격 포트인 skc_dport가 네트워크 오더라서 변환이 필요하다.

07BPF_CORE_READ(sk, __sk_common.skc_daddr)는 중간 단계마다 재배치 정보를 남긴다.

정답 O. -> 연쇄를 따라가며 각 필드 접근에 CO-RE 재배치를 건다. 직접 sk->__sk_common.skc_daddr로 쓰면 빌드 당시 오프셋이 박힌다.

08IPv6 연결은 이 예제에서 이벤트로 올라오지 않지만 개수는 세어진다.

정답 O. Lv3의 주제다. 필터로 버린 것의 개수를 남기지 않으면 나중에 "왜 이 트래픽이 안 잡히지?"에 답할 수 없다.

09fentry는 tracepoint처럼 커널이 미리 선언해 둔 지점에만 붙을 수 있다.

정답 X. BTF에 있는 거의 모든 커널 함수에 붙을 수 있다. 자유도는 kprobe급, 안전성은 tracepoint급 — 그게 fentry의 위치다.

10통계용 PERCPU 배열을 증가시킬 때 bump()는 원자 연산을 쓰지 않는다.

정답 O. PERCPU라 CPU마다 복사본이 따로 있고 경쟁이 없다. 일반 HASH/ARRAY였다면 __sync_fetch_and_add가 필요하다.

11kprobe로 반환값을 보려면 kretprobe를 따로 붙이고 인자는 맵에 저장해 둬야 한다.

정답 O. 그 저장/회수 과정에서 맵이 하나 더 필요하고, 반환을 못 잡으면 누수가 생긴다. fexit은 이 과정을 통째로 없앤다.

12fentry는 kprobe보다 오버헤드가 크다.

정답 X. 반대다. 트랩/예외 경로 대신 트램폴린 점프라서 함수 호출 한 번 수준이다. 실무 에이전트가 kprobe에서 fentry로 옮긴 주된 이유다.
