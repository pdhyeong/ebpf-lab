ebpf-lab/예제 04/uprobe (Go 바이너리)

커널 밖으로 나가는 훅

eBPF인데 대상이 커널이 아니다. 내가 만든 Go 프로그램의 함수에 붙어서 인자를 읽는다. Frida를 써 봤다면 가장 익숙한 랩이고, 동시에 Frida와 eBPF의 경계가 가장 선명해지는 랩이다.

00uprobe란 무엇인가

파일의 오프셋에 트랩을 심는다. 프로세스가 아니라 파일이 대상이다.

대상은 프로세스가 아니라 파일 + 오프셋

여기가 Frida와 갈리는 첫 지점이다. Frida는 실행 중인 프로세스에 붙는다. uprobe는 ELF 파일의 특정 오프셋에 등록한다. 그래서:

  • 그 바이너리를 실행하는 모든 프로세스가 자동으로 걸린다 — 지금 것도, 앞으로 뜰 것도.
  • 대상 프로세스가 죽어도 훅은 남아 있다. 다시 뜨면 또 잡힌다.
  • 프로세스 하나만 보려면 -pid로 별도 지정해야 한다.

"이 바이너리를 실행하는 모든 컨테이너의 모든 프로세스"를 한 번에 거는 게 가능하다는 뜻이다. Frida로는 프로세스마다 붙어야 하는 일이다.

동작 — 커널이 관리하는 브레이크포인트

커널이 해당 파일 페이지의 그 오프셋에 트랩 명령을 심는다(copy-on-write로 프로세스별 사본에). 실행이 거기 닿으면 트랩 → 커널 → 내 BPF 프로그램. 프로세스는 자기가 후킹당한 걸 모른다.

Go 함수를 잡을 때의 두 가지 함정

1 · 레지스터 호출 규약

Go 1.17+는 regabi를 쓴다. 첫 정수 인자가 arm64는 X0, amd64는 RAX. BPF_UPROBE 매크로가 PT_REGS_PARM1로 알아서 골라준다. Go 1.16 이하(스택 기반)라면 이 방법이 통하지 않는다.

2 · uretprobe 금지

Go에서 uretprobe를 쓰면 대상 프로세스가 죽을 수 있다. 고루틴 스택이 이동(grow)하면 uretprobe가 심어둔 복귀 주소가 무효화되기 때문이다. 반환값이 필요하면 함수의 return 지점 오프셋에 uprobe를 붙인다.

Frida와 나란히
Fridauprobe + eBPF
대상프로세스파일 오프셋 (그 파일의 모든 프로세스)
인자 읽기args[0] 자유롭게BPF_UPROBE로 받되 메모리는 헬퍼 경유
반환값onLeave 쉽게Go에선 위험 — return 오프셋에 별도 uprobe
값 수정가능 (인자·반환값 변조)불가 — 관찰만
탐지 회피프로세스가 알아챌 수 있음프로세스는 모름 (커널이 관리)

결론: 값을 바꿔야 하면 Frida, 넓게 오래 관찰해야 하면 uprobe다.

01이 랩이 하는 일

target/workload 의 main.compute(n) 진입을 잡아 인자 n 을 읽는다.

target/workload/main.go는 500ms마다 compute(n)을 부르는 단순한 프로그램이다:

func compute(n int) int {
        sum := 0
        for i := 0; i <= n; i++ { sum += i * i }
        return sum
}

이 main.compute의 진입점에 uprobe를 붙여 n을 훔쳐본다. 실제 대상 지정은 Go 쪽에서 한다:

ex, _ := link.OpenExecutable("/opt/lab/bin/workload")
up, _ := ex.Uprobe("main.compute", objs.UprobeCompute, nil)

.bpf.c의 SEC("uprobe/main.compute")는 라벨일 뿐이다 — 실제 파일/심볼과 무관하다. 그래서 같은 BPF 프로그램을 -bin/-sym 플래그로 다른 바이너리에 붙일 수 있다.

이 랩 최대의 함정 · virtiofs

uprobe는 /lab(macOS 바인드 마운트 = virtiofs) 위의 파일에 붙을 수 없다. perf_event_open이 EIO로 실패한다. 그래서 타깃을 컨테이너 자체 파일시스템인 /opt/lab/bin/workload로 빌드한다(make workload). 이건 macOS + Docker Desktop 환경 특유의 문제로, 원인을 모르면 몇 시간을 날린다.

실행

make 04            # workload 를 자동으로 띄우고 붙는다
make 04-check      # 채점
make workload-stop # 타깃 종료

02단계 공략

빈칸 4개. Lv3은 한 줄인데, 그 한 줄이 되는 이유가 이 랩의 핵심이다.

LV 1 · 30점링버퍼 예약
e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);

01번과 같다. 이벤트가 안 나오면 workload가 떠 있는지부터 확인하라 (pgrep -x workload). 채점 스크립트는 자동으로 띄운다.

LV 2 · 25점누가 언제 불렀나
__u64 id = bpf_get_current_pid_tgid();
e->tgid = id >> 32;
e->pid  = (__u32)id;
e->ts   = bpf_ktime_get_ns();
bpf_get_current_comm(&e->comm, sizeof(e->comm));

왜 comm이 workload인가: uprobe는 대상 프로세스의 컨텍스트에서 실행된다. "현재 프로세스"가 곧 후킹당한 프로세스라는 뜻이다. bpf_ktime_get_ns()는 부팅 기준 단조 시각이지 벽시계가 아니다 — main.go가 부팅 시각을 더해서 사람이 읽는 시간으로 바꾼다.

LV 3 · 20점함수 인자 읽기
e->arg = n;

한 줄이다. 그런데 이 한 줄이 되는 이유가 이 랩에서 제일 중요하다:

SEC("uprobe/main.compute")
int BPF_UPROBE(uprobe_compute, long n)
//  ↑ 이 매크로가 내부적으로 PT_REGS_PARM1(ctx) 로 확장된다
//    arm64 → X0,  x86_64 → RAX  (아키텍처를 신경 쓸 필요가 없다)

주의: 인자가 포인터(문자열·슬라이스·구조체)라면 이렇게 못 읽는다. bpf_probe_read_user_str() 등으로 유저 메모리를 복사해야 한다. 여기서는 int라 레지스터 값이 곧 값이다.

LV 4 · 10점인자 기반 필터 (보너스)
if (n < 1000)
        return 0;   // 예약 전에 거르는 게 가장 싸다

이 패턴이 실무의 전부다. "특정 조건의 호출만 본다"를 커널에서 판정하면 유저 공간 비용이 0이 된다. 12번 안티치트 게임이 정확히 이 구조로 "HP가 100을 넘는 비정상 값"을 잡아낸다.

03함정과 확장

uprobe 특유의 문제들.

함정 1 · EIO 로 부착 실패

virtiofs 위의 파일이다. /opt/lab/bin/에 빌드한 바이너리를 대상으로 하라 (make workload). 이 랩에서 가장 자주 막히는 지점이다.

함정 2 · 심볼을 못 찾는다

Go 바이너리가 스트립됐거나 함수가 인라인된 경우다. 확인:
go tool nm /opt/lab/bin/workload | grep main.compute
인라인을 막으려면 //go:noinline을 붙인다. C/C++이면 nm -D로 동적 심볼을 본다.

함정 3 · uretprobe 로 Go 프로세스가 죽는다

절대 쓰지 마라. 고루틴 스택이 이동하면 심어둔 복귀 주소가 무효화된다. 반환값이 필요하면 objdump로 ret 명령 오프셋을 찾아 거기에 uprobe를 붙인다. (C/C++ 처럼 스택이 고정된 언어에서는 uretprobe가 안전하다.)

여기서 확장하면

  • 다른 바이너리 잡기 — make 04 ARGS="-bin /usr/bin/curl -sym main"
  • 라이브러리 함수 — libssl.so의 SSL_write에 붙이면 암호화 전 평문이 보인다. 실무 eBPF 관측 도구들이 실제로 쓰는 기법이다.
  • USDT — 애플리케이션이 미리 심어둔 정적 추적점. uprobe의 tracepoint 버전이라고 보면 된다.

04퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

점수 0 / 12 아직 안 풀었다

A. O / X

01uprobe는 실행 중인 특정 프로세스에 붙는다.

정답 X. ELF 파일의 오프셋에 등록한다. 그래서 그 바이너리를 실행하는 모든 프로세스가 자동으로 걸리고, 앞으로 뜰 프로세스도 걸린다.

02대상 프로세스가 종료되면 uprobe 등록도 함께 사라진다.

정답 X. 훅은 파일 오프셋에 남아 있다. 같은 바이너리가 다시 실행되면 또 잡힌다. 이게 Frida와의 결정적 차이다.

03Go 프로그램에 uretprobe를 붙이면 대상 프로세스가 죽을 수 있다.

정답 O. 고루틴 스택이 이동하면 uretprobe가 심어둔 복귀 주소가 무효화된다. 반환값이 필요하면 return 지점 오프셋에 uprobe를 붙인다.

04SEC("uprobe/main.compute")의 문자열이 실제 대상 심볼을 결정한다.

정답 X. 라벨일 뿐이다. 실제 파일과 심볼은 Go 쪽 link.OpenExecutable(...).Uprobe("main.compute", ...)에서 정한다.

05BPF_UPROBE 매크로 덕분에 arm64와 x86_64에서 같은 코드가 동작한다.

정답 O. 내부적으로 PT_REGS_PARM1로 확장되고, 그게 arm64에서는 X0, x86_64에서는 RAX로 풀린다.

06Go 1.16 이하의 바이너리에서도 이 예제 방식이 그대로 통한다.

정답 X. Go 1.17부터 레지스터 기반 호출 규약(regabi)이다. 그 이전은 스택 기반이라 인자를 스택에서 읽어야 한다.

07uprobe 프로그램 안에서 bpf_get_current_comm()은 후킹당한 프로세스의 이름을 돌려준다.

정답 O. uprobe는 대상 프로세스의 컨텍스트에서 실행되기 때문이다. 그래서 이 랩에서 COMM이 workload로 찍힌다.

08bpf_ktime_get_ns()는 UTC 벽시계 시각을 나노초로 돌려준다.

정답 X. 부팅 기준 단조 시각이다. 사람이 읽는 시간으로 바꾸려면 유저 공간에서 부팅 시각을 더해야 한다 — main.go가 그 일을 한다.

09함수 인자가 문자열 포인터여도 e->arg = n;처럼 바로 값을 담으면 된다.

정답 X. 포인터는 주소일 뿐이다. 내용을 보려면 bpf_probe_read_user_str()로 유저 메모리를 복사해야 한다. 이 랩은 int라 레지스터 값이 곧 값이다.

10uprobe로 함수의 인자 값을 변조할 수 있다.

정답 X. eBPF 트레이싱 프로그램은 관찰만 한다. 값을 바꾸려면 Frida 같은 도구가 필요하다. "바꿀 것인가 볼 것인가"가 두 도구를 가르는 기준이다.

11macOS 바인드 마운트(/lab) 위의 바이너리에는 uprobe를 붙일 수 없다.

정답 O. virtiofs에서 perf_event_open이 EIO로 실패한다. 그래서 타깃을 컨테이너 파일시스템(/opt/lab/bin)에 빌드한다.

12인자 조건으로 걸러야 한다면 링버퍼에 올린 뒤 유저 공간에서 버리는 게 낫다.

정답 X. 커널에서 예약 전에 거르는 게 가장 싸다. 유저 공간까지 올려서 버리면 그게 곧 오버헤드다. 12번 안티치트가 이 구조를 그대로 쓴다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1Go 바이너리에서 대상 심볼이 존재하는지 확인하는 명령은? 
go tool nm /opt/lab/bin/workload | grep main.compute

없다면 스트립됐거나 인라인된 것이다. //go:noinline으로 인라인을 막을 수 있다.

C2유저 공간 문자열 인자를 읽어야 할 때 쓰는 헬퍼는?
______(&buf, sizeof(buf), (void *)ptr); 
bpf_probe_read_user_str(&buf, sizeof(buf), (void *)ptr);

uprobe의 인자 포인터는 항상 유저 공간을 가리킨다. _kernel을 쓰면 조용히 빈 문자열이 나온다.

C3uprobe 타깃 바이너리를 컨테이너 파일시스템에 빌드하는 make 타깃은? 
make workload   # -> /opt/lab/bin/workload

/lab(virtiofs) 위에 두면 perf_event_open이 EIO로 실패한다.
