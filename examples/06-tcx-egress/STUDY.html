ebpf-lab/예제 06/TCX (커널 6.6+)

현대 Cilium이 서 있는 자리

XDP는 빨랐지만 ingress 전용이고 메타데이터가 없었다. TC는 skb가 있는 자리라 양방향이고 정보가 풍부하다. 그리고 커널 6.6부터 생긴 TCX는 qdisc를 만들 필요 없이 bpf_link로 붙는다 — 지금 Cilium 데이터패스가 여기 있다.

00TC와 TCX란 무엇인가

skb가 있는 자리. 그리고 그 자리에 붙는 현대적인 방법.

XDP와 나란히 놓으면

TC → TCX로 바뀐 것

예전 방식은 번거로웠다. clsact qdisc를 netlink로 만들고, 거기에 BPF 필터를 붙였다. 프로그램 여러 개를 순서대로 걸려면 우선순위 숫자를 직접 관리해야 했고, 정리(cleanup)도 수동이었다.

커널 6.6의 TCX는 이걸 bpf_link로 바꿨다:

  • qdisc를 만들 필요가 없다
  • 여러 프로그램의 체이닝을 커널이 관리한다 (TCX_NEXT로 다음으로 넘긴다)
  • fd가 닫히면 자동으로 정리된다 — 죽은 프로그램이 인터페이스에 남지 않는다

반환값

값결과
TCX_NEXT (-1)체인의 다음 프로그램으로 넘긴다 (이 랩)
TC_ACT_OK (0)통과시키고 체인 종료
TC_ACT_SHOT (2)버린다 (14번 IPS 모드)
TC_ACT_REDIRECT다른 인터페이스로 보낸다

01이 랩이 하는 일

한 인터페이스의 양방향 트래픽을 방향별·프로토콜별로 센다.

같은 account() 함수를 tcx_ingress와 tcx_egress 두 프로그램이 방향 값만 바꿔서 호출한다. 통계는 PERCPU_ARRAY에 방향별로 2칸.

loopback에서 왜 양쪽이 다 올라가나

lo에서는 egress로 나간 패킷이 곧바로 ingress로 들어온다. 그래서 ping 127.0.0.1 하나로 두 방향이 동시에 잡힌다. 08·09·14번 게임이 이 성질을 이용해서 한 머신 안에서 변조 → 탐지를 완결시킨다 — 외부 대상이 전혀 없다.

패킷을 읽는 방법이 XDP와 다르다

/* XDP: 포인터 직접 + 경계 검사 */
struct iphdr *ip = (void *)(eth + 1);
if ((void *)(ip + 1) > data_end) return XDP_PASS;
count(ip->protocol);

/* TC/TCX: 헬퍼로 안전하게 복사 */
__u8 ipproto = 0;
if (bpf_skb_load_bytes(skb, 14 + 9, &ipproto, sizeof(ipproto)) < 0)
        return TCX_NEXT;
왜 헬퍼를 쓰나

skb는 조각나 있을 수 있다(non-linear). 선형 영역 밖은 포인터로 접근하면 안 된다. bpf_skb_load_bytes()는 필요하면 조각을 넘어가며 알아서 읽어 준다. 14 + 9는 "이더넷 헤더 14바이트 + IP 헤더 내 protocol 필드 오프셋 9"다.

실행

make 06 ARGS="-iface lo"
# 터미널 B
make sh
ping -c4 127.0.0.1

make 06-check

02단계 공략

빈칸 4개. Lv3이 XDP와의 차이를 몸으로 확인하는 지점이다.

LV 1 · 35점방향별 패킷/바이트
s->packets++;
s->bytes += skb->len;

skb->len에 주목하라. XDP에서는 data_end - data로 직접 계산해야 했다. TC에서는 커널이 이미 채워 놓은 값을 그냥 읽는다 — "메타데이터가 풍부하다"는 말의 구체적인 의미다.

LV 2 · 25점IPv4 프로토콜 분류
__u8 ipproto = 0;
if (bpf_skb_load_bytes(skb, 14 + 9, &ipproto, sizeof(ipproto)) < 0)
        return TCX_NEXT;
switch (ipproto) {
case 1:  s->icmp++; break;
case 6:  s->tcp++;  break;
case 17: s->udp++;  break;
}

그 위의 조건을 눈여겨보라: if (bpf_ntohs(skb->protocol) != ETH_P_IP). skb->protocol은 네트워크 오더로 들어온다. bpf_ntohs를 빼면 IPv4 패킷을 하나도 못 알아본다.

LV 3 · 15점egress 방향
SEC("tc")
int tcx_egress(struct __sk_buff *skb)
{
        return account(skb, DIR_EGRESS);
}

한 줄이지만 이게 TCX의 존재 이유다. XDP로는 애초에 불가능한 일이다. 나가는 트래픽을 봐야 하는 순간 — 데이터 유출 탐지, egress 정책, NAT — 선택지는 TC/TCX뿐이다.

LV 4 · 10점포트 단위 (보너스)
__u16 dport = 0;
bpf_skb_load_bytes(skb, 14 + 20 + 2, &dport, sizeof(dport));
dport = bpf_ntohs(dport);

주의: 14 + 20은 IP 헤더가 20바이트(옵션 없음)라고 가정한 것이다. 정석은 IHL 필드를 읽어 실제 길이를 계산하는 것. 09번 게임이 "IHL이 말이 안 되면 조작된 패킷"이라는 불변식 검사로 이걸 활용한다.

03함정과 다음 단계

TCX 특유의 조건들.

함정 1 · 커널 6.6 미만이면 TCX 가 없다

이 랩의 커널은 6.10이라 문제없다. 구버전 커널에서 같은 일을 하려면 clsact qdisc를 직접 만들고 tc filter로 붙여야 한다. make check가 커널 버전을 확인한다.

함정 2 · 바이트 오더

skb->protocol은 네트워크 오더다. bpf_ntohs를 빼면 IPv4를 하나도 못 알아보고 카운트가 전부 0으로 남는다 — 그런데 에러는 안 난다. 조용한 실패라 원인 찾기가 오래 걸린다.

함정 3 · TCX_NEXT 와 TC_ACT_OK 를 혼동

TCX_NEXT(-1)는 "체인의 다음 프로그램으로", TC_ACT_OK(0)는 "통과시키고 체인 종료". 관찰만 하는 프로그램이 TC_ACT_OK를 돌려주면 뒤에 붙은 다른 프로그램이 안 돌아간다. Cilium 같은 게 이미 붙어 있는 환경에서 사고가 나는 지점이다.

A. O / X

01TC/TCX 프로그램은 skb가 만들어진 뒤에 실행된다.

정답 O. 그래서 skb->len, mark, cgroup 정보 같은 메타데이터를 그냥 읽을 수 있다. 대신 XDP보다 한 단계 느리다.

02TCX는 XDP와 마찬가지로 ingress에만 붙을 수 있다.

정답 X. TC/TCX의 존재 이유가 양방향이다. 나가는 트래픽을 봐야 하는 순간 선택지는 TC/TCX뿐이다.

03TCX를 쓰면 clsact qdisc를 직접 만들 필요가 없다.

정답 O. 커널 6.6부터 bpf_link로 바로 붙는다. 체이닝도 커널이 관리하고, fd가 닫히면 자동 정리된다.

04TC 컨텍스트에서도 XDP처럼 패킷 포인터를 직접 만지는 게 권장된다.

정답 X. skb는 조각나 있을 수 있다(non-linear). bpf_skb_load_bytes()로 읽는 게 관용구다.

05bpf_skb_load_bytes(skb, 14 + 9, ...)의 14는 이더넷 헤더 길이다.

정답 O. 그 다음 +9가 IP 헤더 안에서 protocol 필드의 오프셋이다.

06skb->protocol은 호스트 바이트 오더라서 변환이 필요 없다.

정답 X. 네트워크 오더다. bpf_ntohs를 빼면 IPv4를 하나도 못 알아보고, 에러 없이 카운트만 0으로 남는다.

07TCX_NEXT와 TC_ACT_OK는 같은 의미다.

정답 X. TCX_NEXT(-1)는 체인의 다음 프로그램으로 넘기고, TC_ACT_OK(0)는 통과시키며 체인을 끝낸다. 관찰용 프로그램이 후자를 쓰면 뒤에 붙은 프로그램이 안 돌아간다.

08loopback에서는 egress로 나간 패킷이 곧바로 ingress로 들어온다.

정답 O. 그래서 ping 127.0.0.1 하나로 양방향이 동시에 잡힌다. 08·09·14번 게임이 이 성질로 한 머신 안에서 변조→탐지를 완결시킨다.

09패킷을 실제로 버리려면 TC에서 TC_ACT_SHOT을 반환한다.

정답 O. 14번 IDS/IPS 게임의 IPS 모드가 이 값을 쓴다. 이 랩은 관찰만 하므로 항상 TCX_NEXT다.

10패킷 헤더를 수정하는 작업은 TC가 XDP보다 편하다.

정답 O. skb가 있고 bpf_l3/l4_csum_replace 같은 체크섬 헬퍼가 완비돼 있다. 08번 패킷 변조가 TC에서 이뤄지는 이유다.

1114 + 20 + 2로 TCP 목적지 포트를 읽는 것은 모든 IPv4 패킷에서 안전하다.

정답 X. IP 헤더가 20바이트(옵션 없음)라고 가정한 것이다. 정석은 IHL 필드를 읽어 실제 길이를 계산하는 것. 09번이 이걸 불변식 검사로 활용한다.

12통계용 PERCPU_ARRAY를 쓰면 여러 CPU가 동시에 패킷을 처리해도 락이 필요 없다.

정답 O. CPU마다 복사본이 따로 있기 때문이다. 패킷 처리 경로에 락이 있으면 그게 곧 병목이다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1TC 컨텍스트에서 패킷 바이트를 안전하게 읽는 헬퍼는?
______(skb, 14 + 9, &ipproto, sizeof(ipproto)); 
bpf_skb_load_bytes(skb, 14 + 9, &ipproto, sizeof(ipproto));

skb가 조각나 있어도 알아서 넘어가며 읽어 준다. 반환값이 음수면 실패다 — 반드시 확인해야 한다.

C2XDP에서는 직접 계산해야 했던 패킷 길이를 TC에서는 어디서 읽나? 
s->bytes += skb->len;

XDP였다면 data_end - data다. 커널이 이미 채워 둔 값을 쓰는 게 TC의 이점이다.

C3체인의 다음 BPF 프로그램으로 넘기는 TCX 반환값은? 
#define TCX_NEXT -1
return TCX_NEXT;

TC_ACT_OK(0)를 쓰면 체인이 거기서 끝나 뒤에 붙은 프로그램이 실행되지 않는다.
