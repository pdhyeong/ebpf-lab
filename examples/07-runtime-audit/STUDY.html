00예제와 제품을 가르는 다섯 가지

기능이 되는 것과 믿고 쓸 수 있는 것은 다르다.

훅 하나를 붙이는 건 어렵지 않다. 그걸 프로덕션에 올릴 물건으로 만들 때 반드시 필요해지는 것들이 있다.

1 · 하나의 오브젝트, 여러 프로브

프로브마다 맵과 링버퍼를 따로 만들면 메모리와 관리 비용이 폭발한다. 이벤트에 kind를 실어 하나의 링버퍼로 보낸다.

2 · 커널에서 미리 거른다

유저 공간까지 올려서 버리면 그게 곧 오버헤드다. 그리고 자기 자신을 안 걸러내면 에이전트가 자기 로그를 보고 또 이벤트를 만드는 피드백 루프가 생긴다.

3 · 런타임 설정 맵

재컴파일 없이 켜고 끈다. 실제 제품은 여기에 정책이 들어간다. 유저 → 커널 방향 통신도 결국 맵이다.

4 · 유실 카운터

링버퍼가 꽉 차면 이벤트가 사라진다. 몇 개 잃었는지 모르는 관측 시스템은 신뢰할 수 없다. 반드시 세어서 노출한다.

5 · cgroup id 로 귀속

컨테이너/파드 단위로 묶는 유일하게 믿을 만한 키다. PID는 네임스페이스마다 다르고 재사용된다. cgroup v2에서 cgroup id = 디렉터리 inode 번호다.

+ 컨테이너 이름은 커널에 없다

커널은 cgroup id까지만 안다. "이게 ebpf-victim이다"는 런타임에 물어봐야 알 수 있어서 docker 소켓을 읽는다. 실무에서 권한 범위를 반드시 검토할 지점.

01구조

세 프로브 + 세 맵. 01~06에서 배운 게 전부 한 파일에 있다.

프로브 세 개 — 훅 종류가 다 다르다

이벤트훅배운 랩경로 읽기
EXECtracepoint/syscalls/sys_enter_execve02_user
CONNECTfentry/tcp_connect03—
UNLINKkprobe/do_unlinkat01_kernel

같은 "경로 읽기"인데 헬퍼가 다르다는 게 이 랩의 핵심 교훈 중 하나다. execve는 시스템콜 진입 직후라 포인터가 아직 유저 공간이고, do_unlinkat은 이미 커널로 복사된 뒤다.

맵 세 개

맵타입방향역할
eventsRINGBUF (1MB)커널 → 유저이벤트 스트리밍
config_mapARRAY유저 → 커널런타임 설정 주입
statsPERCPU_ARRAY커널 → 유저종류별 카운트 + 유실 + 필터됨

EXEC 이벤트의 함정 하나

comm 과 path 가 다른 프로세스를 가리킨다

sys_enter_execve 시점에는 아직 새 이미지가 로드되지 않았다. 그래서 comm은 실행을 요청한 쪽(보통 셸)의 이름이고, path가 새로 실행될 파일이다. 이 차이를 모르고 대시보드를 만들면 계속 헷갈린다.

실행

make 07
make 07 ARGS="-json"                       # JSON Lines 로그
make 07 ARGS="-container ebpf-victim"      # 특정 컨테이너만 (커널에서 필터)
make 07 ARGS="-metrics :9101"              # Prometheus — 맥에서 localhost:9101/metrics
make 07 ARGS="-pin"                        # 맵을 /sys/fs/bpf 에 pin

make 07-check

02단계 공략

빈칸 4개. Lv1이 이 랩에서 가장 중요하다.

LV 1 · 30점커널 단계 필터
if (kind == KIND_EXEC && !cfg->want_exec)       return 0;
if (kind == KIND_CONNECT && !cfg->want_connect) return 0;
if (kind == KIND_UNLINK && !cfg->want_unlink)   return 0;

__u32 tgid = bpf_get_current_pid_tgid() >> 32;
if (tgid == cfg->self_pid) { bump(STAT_FILTERED); return 0; }   // 피드백 루프 차단

__u64 cgid = bpf_get_current_cgroup_id();
if (cfg->cgroup_id != 0 && cgid != cfg->cgroup_id) {
        bump(STAT_FILTERED); return 0;
}
*cgid_out = cgid;
return 1;

세 가지가 한 함수에 다 들어 있다:

  • 런타임 설정 — 재컴파일 없이 프로브를 켜고 끈다. 유저 공간이 로드 직후 config_map에 써 넣는다.
  • 자기 자신 차단 — 이게 없으면 에이전트가 로그 파일을 열고, 그 openat이 이벤트가 되고, 그걸 기록하려고 또 파일을 열고… 무한 증폭된다. 실제로 겪어보면 잊지 못한다.
  • 범위 제한 — cgroup id로 컨테이너 하나만 본다. 버린 것도 STAT_FILTERED로 센다.
LV 2 · 25점UID와 부모 PID
e->uid = (__u32)bpf_get_current_uid_gid();

/* 부모 PID 는 헬퍼가 없다. task_struct 를 CO-RE 로 타고 들어간다 */
struct task_struct *task = (struct task_struct *)bpf_get_current_task();
e->ppid = BPF_CORE_READ(task, real_parent, tgid);

real_parent vs parent: ptrace 중이면 parent가 디버거로 바뀐다. 프로세스 계보를 추적할 때는 real_parent가 맞다. 헬퍼가 없으면 구조체를 타고 들어간다 — 이게 실무에서 계속 쓰는 패턴이고, CO-RE가 없으면 못 하는 일이다.

LV 3 · 20점경로 읽기 — user와 kernel
/* EXEC: 시스템콜 진입 직후 → 유저 공간 포인터 */
const char *filename = (const char *)ctx->args[0];
bpf_probe_read_user_str(&e->path, sizeof(e->path), filename);

/* UNLINK: 이미 커널로 복사된 뒤 → 커널 포인터 */
bpf_probe_read_kernel_str(&e->path, sizeof(e->path), BPF_CORE_READ(name, name));

한 파일 안에 둘 다 있다. 바꿔 쓰면 에러 없이 빈 문자열이 나온다. "어느 쪽 메모리인가"를 판단하는 기준은 훅의 위치다 — 시스템콜 경계를 넘기 전인가 후인가.

LV 4 · 10점유실 카운터 (보너스)
e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
if (!e) {
        bump(STAT_DROPPED);   // ← 이 한 줄
        return 0;
}

세 프로브 전부에 넣는다. 종료 시 main.go가 유실=N을 빨간색으로 출력한다. 유실이 보이면 링버퍼를 키우거나(1<<20 → 1<<22) 커널 필터를 더 좁혀야 한다. "모르는 것"과 "0인 것"을 구분할 수 있게 만드는 것이 관측 시스템의 최소 조건이다.

03운영 관점

pinning, 메트릭, 그리고 이 다음.

pinning — 프로세스가 죽어도 남기기

지금까지 모든 랩에서 Go 프로세스가 죽으면 맵과 프로그램도 사라졌다. fd가 닫히면 커널 객체가 회수되기 때문이다. -pin을 주면 /sys/fs/bpf에 파일처럼 고정되어 살아남는다: 

make 07 ARGS="-pin"

# 실행 중에 다른 터미널에서 — 이게 pinning 의 실용성이다
make sh
bpftool map dump pinned /sys/fs/bpf/ebpf-lab/stats

실무에서는 에이전트를 재시작해도 통계가 유지되거나, 별도 CLI가 같은 맵을 읽는 용도로 쓴다. Cilium이 /sys/fs/bpf/tc/globals/에 수십 개 맵을 pin해 두는 것도 같은 이유다 (make cilium-bpf로 볼 수 있다).

Prometheus 메트릭

make 07 ARGS="-metrics :9101"
# macOS 브라우저에서 http://localhost:9101/metrics

PERCPU 통계 맵을 주기적으로 읽어 메트릭으로 노출한다. 유실 카운터를 반드시 메트릭에 포함시키는 게 실무 관례다 — 알림을 걸 대상이기 때문이다.

여기서 확장한다면

  • 정책 맵 — 지금은 on/off뿐이다. "이 경로 접근만 알림" 같은 규칙을 LPM_TRIE나 HASH로 넣으면 Tetragon에 가까워진다.
  • 차단 — 지금은 전부 관찰이다. LSM 훅(10·13번)으로 옮기면 -EPERM으로 막을 수 있다.
  • 이벤트 상관 — EXEC → CONNECT → UNLINK를 PID로 엮으면 "이 프로세스가 뭘 했는가"의 서사가 만들어진다.

학습 트랙 완주

01~07을 다 통과했다면 eBPF의 기본기는 갖춘 것이다. 08~14 게임 트랙은 여기서 배운 것으로 변조·차단·탐지를 직접 구현한다 — 관찰에서 개입으로 넘어가는 단계다.

A. O / X

01프로브마다 링버퍼를 따로 만드는 것이 하나로 합치는 것보다 효율적이다.

정답 X. 맵마다 메모리가 미리 잡히고 관리 비용도 늘어난다. 이벤트에 kind를 실어 하나의 링버퍼로 보내는 게 실무 방식이다.

02에이전트가 자기 자신의 PID를 걸러내지 않으면 이벤트가 무한 증폭될 수 있다.

정답 O. 에이전트가 로그를 쓰고, 그 openat이 이벤트가 되고, 기록하려고 또 파일을 열고… 피드백 루프다. self_pid 필터가 이걸 막는다.

03유저 공간에서 커널로 설정을 전달할 때도 결국 맵을 쓴다.

정답 O. ARRAY 맵(config_map)에 유저 공간이 값을 쓰고 BPF 프로그램이 읽는다. 함수 호출 같은 건 없다.

04링버퍼가 꽉 차서 이벤트가 사라져도, 유실 개수를 세지 않아도 큰 문제는 없다.

정답 X. 몇 개 잃었는지 모르는 관측 시스템은 신뢰할 수 없다. "0인 것"과 "모르는 것"을 구분할 수 있어야 한다.

05cgroup id는 컨테이너 단위로 이벤트를 귀속시키는 신뢰할 만한 키다.

정답 O. PID는 네임스페이스마다 다르고 재사용된다. cgroup v2에서 cgroup id는 cgroup 디렉터리의 inode 번호다.

06커널은 컨테이너의 이름을 알고 있다.

정답 X. 커널에 컨테이너라는 개념이 없다. cgroup id까지만 안다. 이름은 런타임(docker 소켓 등)에 물어봐야 알 수 있다.

07sys_enter_execve 시점의 comm은 새로 실행될 프로그램의 이름이다.

정답 X. 아직 새 이미지가 로드되기 전이라 실행을 요청한 쪽(보통 셸)의 이름이다. 새로 실행될 파일은 path에 있다.

08부모 PID를 얻는 전용 헬퍼가 있다.

정답 X. 없다. bpf_get_current_task()로 task_struct를 얻고 BPF_CORE_READ(task, real_parent, tgid)로 타고 들어가야 한다.

09프로세스 계보를 추적할 때는 parent보다 real_parent가 맞다.

정답 O. ptrace 중이면 parent가 디버거로 바뀐다. 실제 생성 관계는 real_parent다.

10execve의 경로와 unlink의 경로는 같은 헬퍼로 읽으면 된다.

정답 X. execve는 시스템콜 진입 직후라 _user, do_unlinkat은 이미 커널로 복사된 뒤라 _kernel이다. 바꿔 쓰면 에러 없이 빈 문자열이 나온다.

11맵을 pin하면 Go 프로세스가 종료돼도 커널에 남는다.

정답 O. /sys/fs/bpf에 파일처럼 고정된다. 에이전트 재시작 후에도 통계를 유지하거나 별도 CLI가 같은 맵을 읽는 데 쓴다.

12이 예제는 이벤트를 관찰만 하고 차단은 하지 않는다.

정답 O. tracepoint/fentry/kprobe는 전부 관찰용이다. 차단하려면 LSM 훅으로 옮겨 -EPERM을 반환해야 한다(10·13번).

B. 빈칸 채우기

C1현재 프로세스가 속한 cgroup의 id를 얻는 헬퍼는? 
__u64 cgid = bpf_get_current_cgroup_id();

컨테이너/파드 귀속의 유일하게 믿을 만한 키다. cgroup v2에서 이 값은 cgroup 디렉터리의 inode 번호다.

C2부모 PID를 얻으려면?
struct task_struct *task = ______(); 
struct task_struct *task = (struct task_struct *)bpf_get_current_task();
e->ppid = BPF_CORE_READ(task, real_parent, tgid);

헬퍼가 없을 때 구조체를 타고 들어가는 패턴이다. CO-RE가 없으면 커널마다 오프셋이 달라져 못 한다.

C3pin한 맵을 유저 프로그램 없이 읽는 명령은?
