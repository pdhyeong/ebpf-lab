00패킷 변조의 원리

skb를 고치는 건 두 단계다. 값을 쓰고, 체크섬을 맞춘다.

왜 TC인가

XDP는 skb가 없어서 헤더 조작이 제한적이고 체크섬 헬퍼도 빈약하다. TC/TCX는 skb가 있는 자리라 bpf_skb_store_bytes()로 임의 오프셋에 쓸 수 있고, bpf_l3_csum_replace() / bpf_l4_csum_replace()로 체크섬을 증분 갱신할 수 있다. 고칠 거면 TC라는 기준이 여기서 나온다.

두 단계 — 하나라도 빠지면 조용히 죽는다

/* 1) 값 쓰기 */
bpf_skb_store_bytes(skb, IP_TTL_OFF, &new_ttl, 1, 0);

/* 2) 체크섬 증분 갱신 — 이걸 빼면 커널이 패킷을 조용히 버린다 */
bpf_l3_csum_replace(skb, IP_CSUM_OFF, old_ttl, new_ttl, 2);
이 랩에서 배울 단 하나

"코드는 맞는데 통신이 안 된다"의 90%가 체크섬이다. IP/TCP 헤더에서 1바이트만 바꿔도 체크섬이 어긋나면 수신 측 커널이 에러도 로그도 없이 그 패킷을 버린다. 검증 기준은 명확하다 — TTL을 바꿔도 ping 손실이 0%여야 정답이다.

왜 "증분" 재계산인가

체크섬을 처음부터 다시 계산하려면 헤더 전체를 읽어야 한다 — 패킷 경로에서는 비싸다. 인터넷 체크섬은 1의 보수 합이라 "바뀐 값만큼만 빼고 더하는" 산술이 성립한다. 그래서 csum_replace(old, new)로 O(1)에 갱신할 수 있다. 이건 eBPF의 트릭이 아니라 TCP/IP 프로토콜 설계 자체의 성질이다(RFC 1624).

L3와 L4를 구분해야 한다

바꾸는 필드영향받는 체크섬헬퍼
IP TTLIP 헤더만bpf_l3_csum_replace
IP TOS/DSCPIP 헤더만bpf_l3_csum_replace
TCP/UDP 포트L4만 (IP 헤더 불변)bpf_l4_csum_replace
IP 주소둘 다 (L4 의사헤더에 IP가 들어간다)둘 다 호출

IP 주소를 바꿀 때 L4까지 손봐야 하는 이유는 TCP/UDP 체크섬이 의사헤더(pseudo-header)에 출발지·목적지 IP를 포함해 계산되기 때문이다. NAT 구현이 까다로운 근본 원인이다.

01세 가지 동작

config 맵으로 런타임에 고른다. 재컴파일이 없다.

08번은 완성본으로 제공되는 도구다. 채울 빈칸이 없는 대신, 09·14번의 공격 무기로 쓴다.

동작하는 일체크섬
ttlIP TTL을 지정 값으로L3만
dscpIP TOS/DSCP 마킹L3만
dnatTCP 목적지 포트 재작성L4만 — 가장 깔끔한 예

실습

# TTL 을 42 로 — ping 손실 0% 여야 체크섬이 맞은 것
make 08 ARGS="-iface lo -action ttl -ttl 42"

# 목적지 포트 8080 -> 9090 DNAT (양방향)
make 08 ARGS="-iface lo -action dnat -match 8080 -to 9090"
#   터미널 B: nc -lk -p 9090       (서버)
#   터미널 C: nc 127.0.0.1 8080    (8080 을 쳤는데 9090 서버에 붙는다)
loopback 도 이더넷 헤더가 있다

실측 결과 lo도 14바이트 이더넷 헤더를 가진다(MAC이 전부 0일 뿐). 그래서 IP 헤더 오프셋이 eth0과 동일하게 14다. "loopback은 L2가 없다"고 가정하면 전부 어긋난다 — 실측이 문서보다 정확한 대표적인 예.

02DNAT가 단방향이면 왜 TCP가 안 되나

conntrack이 존재하는 이유를 몸으로 확인하는 실험.

나가는 패킷의 목적지 포트를 8080 → 9090으로 바꿨다고 하자. 서버는 9090에서 받는다. 그런데 서버가 응답할 때 출발지 포트는 9090이다. 클라이언트는 8080으로 보냈으니 9090에서 온 패킷을 자기 것으로 인식하지 못한다. TCP는 (출발지IP, 출발지포트, 목적지IP, 목적지포트) 4-튜플로 연결을 식별하기 때문이다.

그래서 역방향에서 9090 → 8080으로 되돌려야 연결이 성립한다. 08번 코드가 그 되돌림을 한다.

직접 해볼 것

역방향 되돌림 코드를 지워보고 nc로 붙어 봐라. TCP 핸드셰이크가 완성되지 않는다. 이게 conntrack(연결 추적)이 존재하는 이유다 — NAT은 "나가는 것만 바꾸면 되는" 일이 절대 아니고, 상태를 기억해야 하는 일이다. 실무 NAT이 어려운 근본 원인을 여기서 눈으로 본다.

A. O / X

01패킷 값을 바꾼 뒤 체크섬을 갱신하지 않으면 커널이 에러를 반환한다.

정답 X. 에러도 로그도 없이 조용히 버린다. "코드는 맞는데 통신이 안 되는" 상황의 대부분이 이것이다.

02TCP 목적지 포트만 바꿀 때는 IP 체크섬도 함께 갱신해야 한다.

정답 X. IP 헤더는 안 건드렸으니 L3 체크섬은 그대로다. bpf_l4_csum_replace만 부르면 된다.

03IP 주소를 바꾸면 L3와 L4 체크섬을 둘 다 갱신해야 한다.

정답 O. TCP/UDP 체크섬이 의사헤더에 출발지·목적지 IP를 포함해 계산되기 때문이다. NAT 구현이 까다로운 근본 원인이다.

04체크섬 증분 재계산은 eBPF가 제공하는 특수한 트릭이다.

정답 X. 인터넷 체크섬이 1의 보수 합이라서 성립하는 프로토콜 설계 자체의 성질이다(RFC 1624). eBPF는 그걸 헬퍼로 노출할 뿐이다.

05loopback 인터페이스에는 이더넷 헤더가 없어서 IP 헤더가 오프셋 0에 있다.

정답 X. MAC이 전부 0일 뿐 14바이트 이더넷 헤더가 있다. IP 헤더 오프셋은 eth0과 같은 14다.

06DNAT를 나가는 방향에만 적용하면 TCP 연결이 성립하지 않는다.

정답 O. 서버 응답의 출발지 포트가 바뀐 포트라서 클라이언트가 자기 연결로 인식하지 못한다. TCP는 4-튜플로 연결을 식별한다.

07패킷을 수정하는 작업은 XDP보다 TC에서 하는 게 낫다.

정답 O. skb가 있어 임의 오프셋 쓰기와 체크섬 헬퍼가 완비돼 있다. XDP는 헤더 조작이 제한적이다.

08TTL을 42로 바꿨는데 ping 손실이 발생한다면 로직이 맞은 것이다.

정답 X. 손실 0%가 정답이다. 손실이 있다는 건 체크섬이 어긋나 수신 측이 버리고 있다는 뜻이다.

09conntrack(연결 추적)은 NAT이 상태를 기억해야 하기 때문에 필요하다.

정답 O. "나가는 것만 바꾸면 되는" 일이 아니다. 역방향을 되돌리려면 어떤 연결을 어떻게 바꿨는지 기억해야 한다.

정답 X. 완성본으로 제공되는 도구다. 09·14번 게임에서 🔴 Red 공격자의 무기로 쓴다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1skb의 특정 오프셋에 값을 쓰는 헬퍼는?
______(skb, IP_TTL_OFF, &new_ttl, 1, 0); 
bpf_skb_store_bytes(skb, IP_TTL_OFF, &new_ttl, 1, 0);

이것만으로는 부족하다. 반드시 체크섬 갱신이 뒤따라야 한다.

C2IP 헤더 체크섬을 증분 갱신하는 헬퍼는?
______(skb, IP_CSUM_OFF, old, new, 2); 
bpf_l3_csum_replace(skb, IP_CSUM_OFF, old_ttl, new_ttl, 2);

TCP/UDP 필드를 바꿨다면 bpf_l4_csum_replace다. IP 주소를 바꿨다면 둘 다.

C3변조가 성공했는지 검증하는 가장 확실한 기준은? 
ping -c10 127.0.0.1   # 손실 0% 여야 체크섬이 맞은 것

TTL 값이 바뀌었는지는 tcpdump로 보고, 손실이 없는지로 체크섬을 검증한다.
