불변식이 깨지는 순간

08번이 패킷을 바꿨다. 그런데 "바뀌었다"는 걸 어떻게 알아채나? loopback 안에서 벌어지는 🔴 Red vs 🔵 Blue 자가 검증 게임이다. 탐지 원리는 실무 IDS와 똑같다 — 당연히 성립해야 할 불변식을 정하고, 깨지면 경보한다.

00탐지의 원리 — 불변식

"정상"을 정의할 수 있어야 "비정상"을 잡는다.

침입 탐지의 출발점은 언제나 같다. 이 환경에서 반드시 참이어야 하는 명제(invariant)를 정하고, 그게 깨지는 순간을 잡는다. 시그니처 기반(14번)과 대비되는 이상 탐지(anomaly detection) 계열이다.

불변식깨지면이 게임의 슬롯
loopback 로컬 트래픽의 TTL은 항상 64누가 경로에서 건드렸다ALERT_TTL
목적지 포트는 아는 서비스 포트리다이렉트 의심ALERT_PORT
IP 헤더의 IHL이 말이 된다조작된 패킷ALERT_BADHDR

왜 TTL 64인가

리눅스의 기본 TTL은 64다. loopback은 라우터를 하나도 안 거치므로 감소할 이유가 없다. 즉 lo에서 TTL이 64가 아니면 누군가 손댔다는 뜻이다. 08번이 42로 바꾸면 그 순간 불변식이 깨진다.

이게 실무에서 통하는 이유

"환경의 제약이 강할수록 불변식이 강해진다." 인터넷 전체를 감시하면 TTL은 아무 의미가 없지만, 내 클러스터 내부 통신이라면 홉 수가 고정이라 강한 신호가 된다. Cilium이 파드 간 트래픽에 대해 강한 정책을 걸 수 있는 것도 같은 이유다 — 범위를 좁히면 탐지가 쉬워진다.

01게임 구조

한 머신 안에서 공격과 탐지가 완결된다.

loopback은 egress로 나간 패킷이 곧바로 ingress로 들어온다. 그래서 외부 대상 없이 자가 검증이 된다.

🔴 Red  = 08번 변조기 (TCX egress 에서 TTL 을 42 로)
              ↓  loopback
🔵 Blue = 09번 탐지기 (TCX ingress 에서 TTL != 64 를 잡는다)

실행 순서

# 터미널 A — 🔵 Blue 탐지기 (심판)
make 09

# 터미널 B — 🔴 Red 공격
make 08 ARGS="-iface lo -action ttl -ttl 42"

# 터미널 C — 트래픽 발생
make sh
ping -c5 127.0.0.1

# 채점
make 09-check

맵 구성

  • dconfig_map (ARRAY) — 감시 포트, TTL 검사 on/off. 유저 → 커널 설정 주입
  • alerts (RINGBUF) — 경보 스트리밍. 경보는 드물어야 하므로 ringbuf가 맞다
  • dstats (PERCPU_ARRAY) — 검사한 패킷 수 + 종류별 경보 수

검사한 패킷 수(STAT_SEEN)를 세는 게 중요하다. 경보 0건이 "공격이 없었다"인지 "탐지기가 아예 안 돌았다"인지 구분해 주는 유일한 값이다.

LV 1TTL 불변식

IP 헤더에서 TTL을 읽어 EXPECTED_TTL(64)과 다르면 경보를 올린다.

__u8 ttl = 0;
bpf_skb_load_bytes(skb, IP_OFF + 8, &ttl, sizeof(ttl));
if (cfg->check_ttl && ttl != EXPECTED_TTL) {
        /* alerts 링버퍼에 ALERT_TTL 로 경보 */
}

경보에 got과 expected를 둘 다 실어라. "이상하다"만 알려주는 경보는 쓸모가 없다. 무엇이 어떻게 달랐는지가 있어야 대응이 된다.

LV 2포트 정책

watch_port로 오는 트래픽 중 allow_port가 아닌 것을 잡는다. 08번의 DNAT 공격(8080 → 9090)을 탐지하는 경로다.

LV 3헤더 무결성 (IHL)

IP 헤더의 IHL 필드가 5 미만이거나 패킷 길이보다 크면 조작된 패킷이다. 06번 Lv4에서 "IP 헤더 20바이트 가정은 위험하다"고 했던 그 필드를 여기서는 탐지 신호로 쓴다.

03오탐 — 이 게임의 진짜 주제

채점 배점을 보면 설계 의도가 보인다.

09번 채점표를 보면 배점이 이렇게 잡혀 있다:

✅ [ 20점] 빌드
✅ [ 30점] 평상시 오탐 없음        경보 0
✅ [ 50점] TTL 변조 탐지          경보 5 🚨
왜 "안 잡는 것"에 30점을 주나

탐지기를 만들 때 제일 쉬운 부정행위는 "다 잡는 것"이다. 무조건 경보를 올리면 탐지율 100%다. 그래서 채점기가 공격이 없는 상태를 먼저 돌려서 경보가 0인지 확인한다. 실무에서 IDS가 실패하는 이유의 대부분도 미탐이 아니라 오탐 피로다 — 경보가 하루 수천 건이면 아무도 안 본다.

14번이 IPS를 다룰 때 "보통 IDS로 한참 관찰한 뒤에야 IPS로 승격한다"고 하는 것도 같은 맥락이다. 오탐이 있는 상태로 차단을 걸면 정상 트래픽이 끊긴다.

확장

  • 경보에 속도 제한을 걸어라. 같은 출발지에서 초당 N건 이상이면 묶어서 하나로 — 링버퍼 유실 방지.
  • 불변식을 유저 공간에서 학습시켜라. 처음 1분은 관찰만 하고 정상 범위를 만든 뒤 config에 주입.

A. O / X

01불변식 기반 탐지는 시그니처 기반 탐지와 같은 방식이다.

정답 X. 불변식(이상 탐지)은 정상을 정의하고 벗어남을 잡고, 시그니처(14번)는 알려진 악성 패턴을 찾는다. 접근이 반대다.

02loopback 로컬 트래픽의 TTL이 64가 아니면 누군가 손댔다고 볼 수 있다.

정답 O. 리눅스 기본 TTL이 64이고 loopback은 라우터를 거치지 않으므로 감소할 이유가 없다. 범위가 좁을수록 불변식이 강해진다.

03탐지 범위를 넓게 잡을수록 불변식이 강해진다.

정답 X. 반대다. 인터넷 전체에서는 TTL이 아무 의미가 없지만 내 클러스터 내부라면 강한 신호가 된다. 범위를 좁히면 탐지가 쉬워진다.

04경보에는 관측값과 기대값을 함께 실어야 한다.

정답 O. "이상하다"만 알려주는 경보는 대응할 수 없다. 무엇이 어떻게 달랐는지가 있어야 한다.

05검사한 패킷 수를 따로 세는 것은 불필요한 낭비다.

정답 X. 경보 0건이 "공격이 없었다"인지 "탐지기가 안 돌았다"인지 구분해 주는 유일한 값이다.

0609번 채점에서 "평상시 오탐 없음"에도 배점이 있다.

정답 O. 30점이다. 무조건 경보를 올리면 탐지율 100%가 되는 부정행위를 막기 위해서다.

07실무에서 IDS가 실패하는 주된 이유는 미탐(놓침)이다.

정답 X. 대부분 오탐 피로다. 경보가 하루 수천 건이면 아무도 보지 않는다.

08loopback에서는 egress로 나간 패킷이 ingress로 들어오기 때문에 자가 검증이 가능하다.

정답 O. 외부 대상 없이 한 머신 안에서 🔴 변조 → 🔵 탐지가 완결된다. 08·09·14번이 전부 이 성질을 이용한다.

09IP 헤더의 IHL 값이 5보다 작으면 정상적인 패킷일 수 있다.

정답 X. IHL은 32비트 워드 단위이고 최소 헤더가 20바이트라 5가 하한이다. 그보다 작으면 조작된 패킷이다.

10탐지기는 08번 변조기와 같은 방향(egress)에 붙는다.

정답 X. 변조기는 egress, 탐지기는 ingress다. 나갈 때 바뀐 패킷이 들어올 때 검사받는 구조다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1IP 헤더에서 TTL을 읽으려면 오프셋이 얼마인가? 
bpf_skb_load_bytes(skb, IP_OFF + 8, &ttl, sizeof(ttl));
/* IP_OFF = ETH_HLEN = 14, TTL 은 IP 헤더 내 +8 */

loopback도 14바이트 이더넷 헤더가 있다는 걸 잊으면 전부 어긋난다.

C2경보가 하나도 없을 때 "탐지기가 돌긴 했는가"를 어떻게 아나? 
STAT_SEEN  /* 검사한 IPv4 패킷 수 */

"0인 것"과 "모르는 것"을 구분할 수 있게 만드는 게 관측 시스템의 최소 조건이다.

C3오탐(false positive)을 채점에서 확인하는 방법은? 
# 공격 없이 정상 트래픽만 발생시킨 뒤 경보가 0인지 확인
ping -c5 127.0.0.1   # -> 경보 0 이어야 통과

탐지율만 보면 "다 잡는" 부정행위를 걸러낼 수 없다.
