00LSM이란 무엇인가

커널이 "허가할까요?"라고 묻는 지점.

LSM 훅의 위치

LSM(Linux Security Module)은 SELinux·AppArmor가 쓰던 그 프레임워크다. 커널의 보안 결정 지점마다 훅이 심어져 있고, 0이 아닌 값을 돌려주면 그 작업이 거부된다. BPF LSM은 여기에 내 BPF 프로그램을 끼워 넣는 것이다. 

execve() → ... → security_bprm_check() → 실제 실행
                        ↑
                  여기서 -EPERM 을 돌려주면 Operation not permitted

트레이싱 훅과 무엇이 다른가

kprobe / tracepoint / fentryLSM
반환값의미 없음 (그냥 0)0 = 허가, 음수 = 거부
호출 시점이미 진행 중결정 직전
할 수 있는 일기록차단
실패의 무게이벤트 하나 놓침정상 동작이 막힘
무게가 다르다

트레이싱 프로그램의 버그는 "로그가 이상하다"로 끝난다. LSM 프로그램의 버그는 시스템을 못 쓰게 만든다. 예를 들어 조건을 잘못 써서 모든 execve를 막으면 새 프로세스를 하나도 못 띄운다 — 복구하려면 이미 떠 있는 셸이 있어야 한다. 이 랩이 컨테이너 안에서 도는 게 다행인 이유다.

전제 조건

커널이 CONFIG_BPF_LSM=y여야 하고, 부팅 파라미터의 lsm= 목록에 bpf가 있어야 한다. 이 랩의 커널은 capability,bpf라 실제로 차단이 된다. make check가 확인해 준다.

01이 게임

"malware"로 끝나는 실행 파일의 실행을 막는다.

lsm/bprm_check_security 훅에서 실행하려는 파일 이름을 검사하고, 시그니처가 맞으면 -EPERM을 반환한다.

실행

make 10

# 다른 터미널
make sh
cp /bin/echo /tmp/malware
/tmp/malware          # 채운 뒤: Operation not permitted

make 10-check

파일 이름은 어디서 오나

struct linux_binprm에 실행하려는 파일 정보가 들어 있다. CO-RE로 file → f_path.dentry → d_name.name을 타고 들어가 이름을 얻는다: 

const unsigned char *name = BPF_CORE_READ(bprm, file, f_path.dentry, d_name.name);
bpf_probe_read_kernel_str(&buf, sizeof(buf), name);
왜 경로 전체가 아니라 파일명인가

d_name은 그 dentry의 마지막 요소일 뿐이다. 전체 경로를 만들려면 부모 dentry를 루트까지 거슬러 올라가야 하는데, BPF의 루프 제약 때문에 까다롭다 (커널 5.10+의 bpf_d_path() 헬퍼가 이 문제를 푼다 — 단, 호출 가능한 훅이 제한적이다). 실무 백신·EDR도 같은 이유로 1차 필터를 이름/확장자로 하고 2차를 내용으로 한다 — 13번이 그 구조다.

통계 슬롯

gstats[0] = 검사한 exec 수, gstats[1] = 차단한 수. 09번과 같은 이유로 "검사는 했는데 차단은 0"과 "아예 안 돌았다"를 구분해야 한다.

02차단 로직의 위험

문자열 비교 하나에 시스템이 걸려 있다.

문자열 매칭의 함정

BPF에는 strstr()이 없다. 직접 비교해야 하는데, 여기서 실수가 나기 쉽다:

  • 길이를 안 재고 비교 — 버퍼 끝을 넘어가면 verifier가 거부한다(다행이다).
  • 널 종료를 안 확인 — bpf_probe_read_kernel_str()은 널을 붙여주지만 반환값(복사 길이)을 확인하는 게 안전하다.
  • 루프 상한이 상수가 아님 — verifier가 종료를 증명 못 하면 거부한다. #pragma unroll이나 고정 길이 비교를 쓴다.

조건을 넓게 잡으면 벌어지는 일

/* 위험: 이러면 /bin/ls 도, make 도, 셸도 전부 막힌다 */
if (buf[0] != 0)
        return -EPERM;
실습 중 시스템이 잠기면

새 명령을 하나도 못 실행하게 된다. 이미 떠 있는 셸에서 실행 중인 make 10을 Ctrl-C로 죽이면 fd가 닫히면서 훅이 해제된다. 그것도 안 되면 컨테이너를 재시작하면 된다(docker compose restart lab) — BPF 프로그램은 프로세스에 묶여 있으므로 컨테이너가 죽으면 같이 사라진다. pinning을 안 하는 게 이럴 때는 안전장치가 된다.

실무에서의 배치 순서

  1. 관찰 모드로 먼저 — 차단 없이 "막았을 것"만 기록한다(dry-run)
  2. 며칠 돌려 오탐 목록을 만든다
  3. 예외를 넣고 나서야 차단으로 승격

14번의 IDS → IPS 승격과 정확히 같은 절차다. 차단은 항상 관찰 다음이다.

04퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

점수 0 / 10 아직 안 풀었다

A. O / X

01LSM 훅에서 0이 아닌 값을 반환하면 해당 작업이 거부된다.

정답 O. -EPERM을 돌려주면 Operation not permitted가 된다. 트레이싱 훅의 반환값이 의미 없는 것과 대비된다.

02kprobe에서도 -EPERM을 반환하면 시스템콜을 막을 수 있다.

정답 X. 트레이싱 훅의 반환값은 무시된다. 차단하려면 LSM처럼 결정 지점에 있는 훅이어야 한다.

03BPF LSM을 쓰려면 부팅 파라미터의 lsm= 목록에 bpf가 있어야 한다.

정답 O. CONFIG_BPF_LSM=y만으로는 부족하다. 이 랩의 커널은 capability,bpf라 실제로 차단된다.

04LSM 프로그램의 버그는 트레이싱 프로그램의 버그보다 영향이 크다.

정답 O. 트레이싱은 로그가 이상해지는 정도지만, LSM은 정상 동작이 막힌다. 조건을 넓게 잡으면 새 프로세스를 하나도 못 띄운다.

05실습 중 모든 exec가 막히면 컨테이너를 재시작해서 복구할 수 있다.

정답 O. BPF 프로그램은 로더 프로세스의 fd에 묶여 있다. 프로세스나 컨테이너가 죽으면 같이 사라진다. pin하지 않은 게 안전장치가 된다.

06d_name.name으로 파일의 전체 경로를 얻을 수 있다.

정답 X. 그 dentry의 마지막 요소(파일명)일 뿐이다. 전체 경로는 부모를 거슬러 올라가야 하는데 BPF 루프 제약 때문에 까다롭다.

07BPF 프로그램 안에서 strstr()을 쓸 수 있다.

정답 X. 표준 라이브러리가 없다. 고정 길이 비교나 #pragma unroll로 직접 구현해야 하고, 루프 상한이 상수여야 verifier가 통과시킨다.

08차단 기능은 관찰 없이 바로 프로덕션에 켜는 게 효율적이다.

정답 X. 관찰(dry-run) → 오탐 목록 → 예외 추가 → 차단 승격이 실무 순서다. 14번의 IDS → IPS 승격과 같은 절차다.

09lsm/bpf 훅으로 다른 BPF 프로그램의 로드를 막을 수 있다.

정답 O. 보안 에이전트가 자기 자신을 무력화당하지 않게 지키는 데 쓴다.

10검사한 exec 수와 차단한 수를 따로 세는 것은 의미가 없다.

정답 X. "검사는 했는데 차단은 0"과 "아예 안 돌았다"를 구분해 준다. 09번의 STAT_SEEN과 같은 이유다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1LSM 훅에서 작업을 거부하려면 무엇을 반환하나? 
return -EPERM;   /* Operation not permitted */

0을 반환하면 허가다. 이 반환값이 트레이싱 훅과 LSM을 가르는 결정적 차이다.

C2실행하려는 파일의 이름을 얻는 CO-RE 경로는? 
const unsigned char *name =
        BPF_CORE_READ(bprm, file, f_path.dentry, d_name.name);
bpf_probe_read_kernel_str(&buf, sizeof(buf), name);

-> 연쇄를 CO-RE로 타고 들어간다. 커널 구조체가 깊을수록 CO-RE의 가치가 커진다.

# 그래도 안 되면
