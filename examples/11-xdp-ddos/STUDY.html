00SYN flood와 XDP

왜 하필 최전선이어야 하나.

공격의 구조

TCP 3-way handshake는 SYN → SYN-ACK → ACK다. 서버는 SYN을 받으면 연결 상태를 만들어 두고 ACK를 기다린다. 공격자는 SYN만 초당 수천 개 퍼붓고 핸드셰이크를 완성하지 않는다. 서버의 half-open 큐가 차면 정상 연결도 못 받는다. 자원 고갈 공격이다.

어디서 막느냐가 비용을 결정한다

NIC → 드라이버 → XDP → skb 할당 → conntrack → netfilter → 소켓
                   ↑                ↑                    ↑
                 여기서 드롭     여기부터 비용      iptables 는 여기
                 = 거의 0        (메모리 할당)     = 이미 다 치렀다

iptables로 드롭해도 skb는 이미 만들어졌고 conntrack도 돌았다. 대용량 공격에서는 그 비용 자체가 서비스를 죽인다. XDP에서 떨구면 버릴 패킷에 대해 거의 아무것도 지불하지 않는다 — 이게 XDP의 존재 이유다.

이 게임

make 11 ARGS="-iface lo -rate 50"
make 11-check     # SYN flood 를 쏴서 임계값 초과분이 차단되는지 채점

01레이트 리밋 구현

1초 창(window)을 출발지별로 관리한다.

자료구조

struct rate {
        __u64 window_start;  /* 현재 1초 창의 시작 (ns) */
        __u64 count;         /* 이 창에서 본 SYN 개수 */
};
/* 키 = 출발지 IP, 맵 타입 = LRU_HASH */

알고리즘 — 고정 창(fixed window)

  1. SYN인지 확인한다 (TH_SYN 세트, TH_ACK 안 세트 → 첫 SYN)
  2. 출발지 IP로 rate를 찾는다. 없으면 새로 만든다
  3. now - window_start > 1초면 창을 리셋한다 (window_start = now, count = 0)
  4. count++
  5. count > syn_per_sec면 XDP_DROP, 아니면 XDP_PASS
SYN 판별을 정확히

SYN|ACK는 서버의 응답이다. 이걸 같이 세면 정상 서버 트래픽이 차단된다. SYN이 세트이고 ACK가 세트가 아닌 것만 새 연결 시도로 봐야 한다. 09번에서 배운 "오탐이 진짜 문제"가 여기서도 그대로 적용된다.

고정 창의 약점

창 경계에서 2배까지 통과할 수 있다. 임계값이 50이면 창 끝에 50개, 다음 창 시작에 50개 — 실질적으로 0.1초 안에 100개가 지나간다. 정교하게 하려면 슬라이딩 윈도우나 토큰 버킷을 쓴다. DDoS 방어에서는 대개 이 정도 오차가 허용된다 — 완벽함보다 처리량이 중요한 영역이다.

02왜 LRU 해시맵인가

이 게임에서 자료구조 선택이 곧 방어력이다.

DDoS는 출발지 IP가 많다. 스푸핑까지 하면 사실상 무한하다. 일반 HASH 맵을 쓰면 max_entries가 차는 순간 새 항목 삽입이 실패하고, 그때부터 새로 오는 공격 IP를 아예 추적하지 못한다. 공격자가 맵을 채워서 방어를 무력화하는 것이 가능해진다.

HASHLRU_HASH
가득 찼을 때삽입 실패 (E2BIG)가장 오래된 항목 축출
공격자가 키를 무한 생성하면방어 무력화최근 활동 IP는 계속 추적
메모리고정고정
적합한 곳키 종류가 한정적키가 폭발하는 곳 (IP, 파일 경로)
02번 Lv4와 이어진다

02번에서 "파일 경로를 키로 하면 맵이 폭발한다 → LRU를 써라"고 했던 그 이야기다. 키의 종류를 내가 통제할 수 없으면 LRU가 기본값이다. 여기서는 그 선택이 보안적으로도 의미를 갖는다 — 자료구조 선택 자체가 공격 표면이다.

시간은 어디서 얻나

__u64 now = bpf_ktime_get_ns();   /* 부팅 기준 단조 시각 */

벽시계(bpf_ktime_get_boot_ns, real)를 쓰면 NTP 보정이나 시간 되감기에 영향을 받는다. 레이트 리밋에는 반드시 단조 시각을 쓴다.

03한계와 실무

이 방식으로 못 막는 것.

출발지 IP 기반의 한계

  • IP 스푸핑 — 출발지를 매번 위조하면 IP별 카운트가 무의미하다. 실무에서는 SYN cookie(상태를 안 만드는 핸드셰이크)와 병행한다.
  • NAT 뒤의 정상 사용자 — 회사 전체가 하나의 공인 IP로 나오면 그 IP가 차단된다. 정상 트래픽을 끊는 오탐이다.
  • 분산 공격 — IP 하나당 임계값 아래로 조절하면 통과한다. 총량 기반 방어가 별도로 필요하다.

그래서 실무는 계층으로 방어한다

  1. 총량 임계 감지 (전체 SYN rate)
  2. IP별 레이트 리밋 (이 게임)
  3. SYN cookie (상태를 안 만든다)
  4. 상위 네트워크에서의 흡수 (Anycast, 스크러빙 센터)

eBPF는 2번을 아주 싸게 만든다. 그게 이 기술이 DDoS 방어에서 차지하는 자리다.

확장

  • 차단된 IP를 ringbuf로 알림 — 유저 공간에서 로그/메트릭
  • 임계값을 동적으로 — 평상시 관찰값의 N배로 자동 조정
  • 화이트리스트 — LPM_TRIE로 CIDR 예외 (Cilium이 쓰는 자료구조)

04퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

A. O / X

01SYN flood는 대역폭이 아니라 서버의 연결 상태 자원을 고갈시키는 공격이다.

정답 O. 서버가 SYN마다 half-open 상태를 만들어 두고 ACK를 기다리는 성질을 악용한다.

02iptables로 드롭하는 것과 XDP로 드롭하는 것은 비용이 비슷하다.

정답 X. iptables 시점에는 이미 skb가 만들어졌고 conntrack도 돌았다. XDP는 그 앞이라 버릴 패킷에 거의 아무 비용도 안 든다.

03SYN|ACK 패킷도 새 연결 시도로 세어야 한다.

정답 X. SYN|ACK는 서버의 응답이다. 같이 세면 정상 서버 트래픽이 차단된다. SYN만 세트인 것을 골라야 한다.

04DDoS 방어용 IP별 카운터에는 일반 HASH 맵보다 LRU_HASH가 적합하다.

정답 O. 공격은 출발지 IP가 많다. HASH는 가득 차면 삽입이 실패해 공격자가 맵을 채워 방어를 무력화할 수 있다.

05레이트 리밋의 시간 기준으로는 벽시계 시각이 적합하다.

정답 X. NTP 보정이나 시간 되감기에 영향을 받는다. bpf_ktime_get_ns()의 단조 시각을 써야 한다.

06고정 창(fixed window) 방식은 창 경계에서 임계값의 2배까지 통과할 수 있다.

정답 O. 창 끝과 다음 창 시작에 몰리면 그렇다. 정교하게 하려면 슬라이딩 윈도우나 토큰 버킷이지만, DDoS 방어에서는 대개 이 오차가 허용된다.

07출발지 IP 기반 레이트 리밋으로 IP 스푸핑 공격도 막을 수 있다.

정답 X. 출발지를 매번 위조하면 IP별 카운트가 무의미하다. 실무에서는 SYN cookie와 병행한다.

08NAT 뒤에 있는 정상 사용자 다수가 한 IP로 보이면 오탐이 발생할 수 있다.

정답 O. 회사 전체가 하나의 공인 IP로 나오면 그 IP가 차단된다. 09번에서 배운 오탐 문제가 여기서도 그대로다.

0905번 예제와 11번 게임은 붙는 훅이 다르다.

정답 X. 같은 XDP 훅이다. 차이는 반환값 — 05번은 항상 XDP_PASS, 11번은 조건에 따라 XDP_DROP이다.

10키의 종류를 프로그램이 통제할 수 없는 경우 LRU 맵이 기본 선택이다.

정답 O. IP, 파일 경로처럼 키가 폭발하는 곳이다. 02번 Lv4의 "파일 경로를 키로 하면 맵이 터진다"와 같은 이야기다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1DDoS 방어에서 출발지 IP를 키로 쓸 때 적합한 맵 타입은? 
__uint(type, BPF_MAP_TYPE_LRU_HASH);

가득 차면 가장 오래된 항목을 자동 축출한다. 일반 HASH는 삽입이 실패해 방어가 무력화된다.

C2레이트 리밋 창 관리에 쓸 시각을 얻는 헬퍼는? 
__u64 now = bpf_ktime_get_ns();   /* 부팅 기준 단조 시각 */

벽시계는 NTP 보정으로 뒤로 갈 수 있다. 시간 차 계산에는 반드시 단조 시각을 쓴다.

C3패킷을 최전선에서 버리는 XDP 반환값은? 
return XDP_DROP;

05번은 같은 자리에서 항상 XDP_PASS였다. 반환값 하나가 관찰과 방어를 가른다.
