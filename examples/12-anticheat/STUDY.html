클라이언트는 믿을 수 없다

04번은 uprobe로 함수 인자를 읽기만 했다. 12번은 그 값을 게임 규칙과 대조해 판정한다. 치트 프로그램의 소스를 고치지 않고, 게임 바이너리에 손대지 않고, 커널에서 메모리 조작을 탐지한다.

00안티치트가 서는 자리

서버 검증이 정석이다. 그런데 왜 클라이언트 감시도 하나.

전제 — 클라이언트는 적의 손에 있다

게임 클라이언트는 사용자 기계에서 돈다. 치트 프로그램은 게임 프로세스의 메모리를 직접 읽고 쓴다 — 체력, 재화, 좌표를 비정상 값으로 바꾼다. 클라이언트가 보내는 값은 아무것도 믿을 수 없다.

정석은 서버가 모든 것을 검증하는 것이다. 하지만 현실에서는:

  • 모든 상태를 서버에서 계산하면 지연과 서버 비용이 감당이 안 된다
  • 물리·에임처럼 클라이언트에서 계산할 수밖에 없는 것들이 있다
  • 서버 검증을 통과하는 범위 안에서의 미세한 이득(에임봇, 월핵)은 값으로 안 잡힌다

그래서 실무 안티치트는 클라이언트 무결성 감시를 병행한다. 12번은 그 축소판이다.

왜 커널에서 하나

방식치트가 무력화하는 법
게임 안에 검사 코드바이너리 패치 / 메모리에서 검사 루틴 무력화
유저 공간 감시 프로세스프로세스 종료 / ptrace 차단 / 후킹
커널 eBPF루트 권한이 필요하다 — 난이도가 급격히 올라간다
Frida 사용자 관점

네가 Frida로 하던 일의 반대편이다. Frida로 게임 함수를 후킹해 값을 바꾸는 게 공격이라면, 12번은 그 후킹당한 호출을 커널에서 관측하는 방어다. 재미있는 건 기법이 거의 같다는 것 — 둘 다 함수 진입점에 훅을 걸고 인자를 본다. 다른 건 어느 레이어에 있느냐뿐이다. 그리고 더 아래 레이어가 이긴다.

01이 게임

setHealth(hp)의 인자가 규칙을 위반하는 순간을 잡는다.

게임 규칙: 체력은 100을 넘을 수 없다(MAX_HP). main.setHealth에 uprobe를 붙여 인자를 검사한다.

  • 정상 setHealth(90~100) → 통과
  • 치트 setHealth(9999) → 경보

실행

make game                              # 실습용 게임 타깃 빌드
make 12                                # 안티치트(심판)

# 다른 터미널
make sh
/opt/lab/bin/game -cheat               # 치트 실행 (HP=9999)

make 12-check

04번과 무엇이 다른가

훅도 같고 인자 읽는 법도 같다. 차이는 그 값으로 무엇을 하느냐다. 

/* 04번: 그냥 담는다 */
e->arg = n;

/* 12번: 규칙과 대조하고, 위반일 때만 올린다 */
if (hp <= MAX_HP)
        return 0;              // 정상은 커널에서 버린다
/* ... cheat_evt 에 value=hp, limit=MAX_HP 를 실어 경보 ... */
04번 Lv4가 여기로 이어진다

04번의 보너스 과제가 "인자 기반 필터 — 커널에서 조건 판정"이었다. 12번은 그 필터가 곧 탐지 로직인 경우다. 정상 호출은 초당 수십~수백 건인데 위반은 드물다 — 커널에서 거르지 않으면 정상 트래픽이 유저 공간을 채운다.

경보에 value(위반값)와 limit(한계)를 둘 다 싣는 것도 09번과 같은 이유다. "치트다"만으로는 대응이 안 된다. 얼마나 벗어났는지가 있어야 오탐 판별과 조치 수위를 정할 수 있다.

02왜 탐지만 하고 차단은 안 하나

기술적으로는 막을 수 있는데, 안 막는 이유가 있다.

uprobe는 관찰 전용이다. 반환값으로 함수 호출을 막을 수 없다. 막고 싶다면 LSM(10·13번)이나 프로세스 종료 같은 별도 수단이 필요하다. 그런데 실무 안티치트도 대개 즉시 차단하지 않는다:

  • 즉시 차단 = 치트 개발자에게 피드백을 주는 것이다. "이 값을 쓰면 걸린다"를 알려주면 우회가 빨라진다.
  • 오탐의 대가가 크다. 정상 사용자를 밴하면 그게 곧 사고다.
  • 모아서 한 번에 — 탐지를 쌓아뒀다가 일괄 제재하는 게 우회 비용을 최대화한다(밴 웨이브).
패턴이 반복된다

09번(오탐 30점), 10번(관찰 → 차단 승격), 14번(IDS → IPS), 12번(탐지 후 일괄 제재). 네 게임이 전부 같은 말을 하고 있다 — 탐지와 대응은 다른 문제이고, 대응을 서두르면 탐지가 망가진다.

uprobe 기반 탐지의 한계

  • 함수를 안 거치면 안 잡힌다. 치트가 setHealth()를 부르지 않고 메모리를 직접 쓰면 이 훅은 아무것도 못 본다. 이 게임의 가장 큰 구멍이다.
  • 심볼이 필요하다. 스트립되거나 난독화되면 오프셋을 직접 찾아야 한다.
  • 바이너리가 바뀌면 오프셋이 바뀐다. 게임 패치마다 재조정이 필요하다.

그래서 실무는 여러 층을 겹친다 — 함수 호출 감시, 메모리 무결성 해시, 드라이버/커널 모듈 목록 검사, 서버 측 통계 이상 탐지. 한 층을 뚫어도 다른 층에 걸리게 만드는 게 목적이다.

A. O / X

01게임 클라이언트가 보내는 값은 서버가 반드시 검증해야 한다.

정답 O. 클라이언트는 사용자 기계에서 돌고 치트가 메모리를 직접 조작한다. 클라이언트 감시는 서버 검증의 보완이지 대체가 아니다.

0212번은 04번과 다른 훅을 사용한다.

정답 X. 같은 uprobe다. 차이는 읽은 값으로 무엇을 하느냐 — 04번은 담기만 하고 12번은 규칙과 대조해 판정한다.

03정상 호출도 전부 유저 공간으로 올린 뒤 거기서 판정하는 게 낫다.

정답 X. 정상 호출이 압도적으로 많다. 커널에서 걸러야 유저 공간 비용이 안 든다. 04번 Lv4 보너스가 바로 이 패턴이다.

04uprobe로 치트 함수의 호출 자체를 막을 수 있다.

정답 X. uprobe는 관찰 전용이다. 반환값으로 흐름을 바꿀 수 없다. 막으려면 LSM 훅이나 다른 수단이 필요하다.

05치트가 setHealth()를 부르지 않고 메모리를 직접 쓰면 이 방식은 탐지하지 못한다.

정답 O. 이 게임의 가장 큰 구멍이다. 그래서 실무는 메모리 무결성 해시 등 여러 층을 겹친다.

06탐지 즉시 차단하는 것이 치트 대응의 정석이다.

정답 X. 즉시 차단은 치트 개발자에게 "이 값을 쓰면 걸린다"는 피드백을 준다. 모아서 일괄 제재(밴 웨이브)하는 게 우회 비용을 높인다.

07경보에는 위반값과 한계값을 함께 실어야 한다.

정답 O. "치트다"만으로는 오탐 판별도 조치 수위 결정도 못 한다. 09번 경보 설계와 같은 원칙이다.

08커널에서 감시하는 것이 유저 공간 감시 프로세스보다 우회하기 어렵다.

정답 O. 유저 공간 프로세스는 종료·후킹이 가능하지만, 커널 eBPF를 건드리려면 루트 권한이 필요하다. 더 아래 레이어가 이긴다.

09연사(rate hack) 탐지처럼 이전 상태가 필요한 규칙은 맵에 상태를 저장해야 한다.

정답 O. PID를 키로 마지막 호출 시각을 저장하고 bpf_ktime_get_ns()로 간격을 잰다. 11번 레이트 리밋과 같은 구조다.

10게임 바이너리가 패치되면 uprobe 설정을 다시 맞춰야 할 수 있다.

정답 O. 심볼 오프셋이 바뀐다. uprobe가 파일 오프셋 기반이기 때문에 생기는 유지보수 비용이다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1규칙 위반이 아닐 때 커널에서 바로 버리려면? 
if (hp <= MAX_HP)
        return 0;   /* 정상 호출은 유저 공간까지 안 올린다 */

정상이 압도적으로 많다. 여기서 안 거르면 그게 곧 오버헤드다.

C2연사 치트를 탐지하려면 무엇을 맵에 저장해야 하나? 
/* 키: PID,  값: 마지막 호출 시각 */
__u64 now = bpf_ktime_get_ns();
/* now - last < COOLDOWN 이면 위반 */

이전 상태가 필요한 규칙은 전부 이 패턴이다. 07번의 "enter 저장 → exit 회수"와 같은 구조다.

C3안티치트 프로세스가 강제 종료되는 것을 막으려면 어떤 훅을 쓰나? 
SEC("lsm/task_kill")   /* 특정 PID 로의 시그널을 -EPERM 으로 거부 */

보안 제품이 자기 자신을 지키는 방법이다. lsm/bpf로 다른 BPF 로드를 막는 것도 같은 목적이다.
