00IDS와 IPS

같은 엔진, 다른 배치. 그리고 완전히 다른 리스크.

IDS (탐지)IPS (차단)
동작경보 + 통과경보 + 드롭
반환값TC_ACT_OKTC_ACT_SHOT
배치미러링/탭 가능 (경로 밖)인라인 (경로 위)
오탐의 결과노이즈정상 트래픽 단절
미탐의 결과공격 놓침공격 놓침
장애 시탐지만 멈춤통신이 멈출 수 있다

기술적으로는 반환값 하나 차이다. 운영상으로는 완전히 다른 물건이다. IPS는 트래픽 경로 위에 서 있으므로 자신이 곧 장애점이 된다.

실행

make 14 ARGS="-iface lo -mode ids"    # 탐지만 (경보 + 통과)
make 14 ARGS="-iface lo -mode ips"    # 차단 (경보 + 드롭)

# 다른 터미널
make sh
echo 'x-EVIL-x' | nc -u -w1 127.0.0.1 9999

#   IDS -> 서버는 받고, 경보도 뜬다
#   IPS -> 서버가 못 받는다 (커널이 떨궜다)

make 14-check
모드가 맵에 있는 이유

iconfig 맵으로 런타임에 전환한다. 재컴파일도, 재부착도 없다. 실무에서 "IDS로 관찰하다 IPS로 승격"할 때 트래픽 중단 없이 넘어갈 수 있어야 하기 때문이다. 07번의 config_map이 여기서 운영상의 의미를 갖는다.

01페이로드 스캔

헤더가 아니라 데이터를 본다.

지금까지와 다른 점

05·06·09·11번은 전부 헤더만 봤다 — 프로토콜, 포트, TTL, 플래그. 14번은 페이로드를 본다. 그래서 오프셋 계산이 한 단계 더 깊다: 

이더넷 14 + IP 20 + UDP 8 = 42 바이트 뒤부터가 페이로드
/* SCAN_LEN 40 : 앞 40바이트만 스캔한다 */

왜 앞부분만 보나: 전체를 스캔하면 비용이 패킷 크기에 비례한다. 실무 IDS도 대부분 앞 N바이트만 본다 — 시그니처는 보통 프로토콜 헤더 근처에 있다. 정교한 회피(시그니처를 뒤로 밀기)에는 약하지만, 처리량과의 거래다.

시그니처 매칭

"EVIL"이 페이로드 어디에든 있으면 걸린다. 각 위치에서 4바이트씩 읽어 비교하고 한 칸씩 밀며 반복한다. 

/* 슬라이딩 비교 — 루프 상한이 컴파일 타임 상수여야 한다 */
#pragma unroll
for (int i = 0; i < SCAN_LEN - 4; i++) {
        __u32 chunk = 0;
        if (bpf_skb_load_bytes(skb, payload_off + i, &chunk, 4) < 0)
                break;
        if (chunk == SIG_EVIL)
                /* 히트 */;
}

02verifier의 벽

이 게임에서 가장 오래 막히는 지점.

zero-sized read

bpf_skb_load_bytes()의 크기가 0이 될 수 있으면 verifier가 거부한다.
invalid zero-sized read
"남은 길이만큼 읽자"처럼 변수 크기로 읽으면, verifier가 "그 변수가 1 이상"임을 증명하지 못해서 막힌다. 하한을 증명하는 건 생각보다 까다롭다.

그래서 14번은 각 위치에서 상수 4바이트씩 읽는다. 우회가 아니라 정석적인 대응이다:

  • 크기가 컴파일 타임 상수면 증명할 게 없다
  • 루프 횟수도 상수라 #pragma unroll로 펼칠 수 있다
  • 펼친 결과가 명령어 수 제한을 넘지 않도록 SCAN_LEN을 작게 잡는다
이 제약이 설계를 결정한다

"앞 40바이트만, 4바이트 고정 청크로" 라는 설계는 성능 판단이 아니라 verifier 제약에서 나온 것이다. eBPF에서는 이런 일이 자주 있다 — 무엇을 할 수 있느냐가 어떻게 설계할지를 정한다. 13번에서 "커널에서 파일 전체를 스캔할 수 없다"고 했던 것과 같은 종류의 벽이다.

회피에 약한 이유

  • 단편화 — 시그니처가 두 패킷에 걸쳐 있으면 못 잡는다. 재조립은 커널에서 못 한다.
  • 암호화 — TLS 안은 안 보인다. 실무에서는 TLS 종단 이후나 uprobe로 SSL_write를 잡는다(04번 확장).
  • 위치 이동 — 시그니처를 40바이트 뒤로 밀면 통과한다.

03IDS에서 IPS로 승격하기

네 게임이 반복해서 말한 것.

실무 절차는 항상 같다:

  1. IDS로 배치 — 경보만, 트래픽에 영향 없음

  3. 오탐 목록 작성 — 정상인데 잡힌 것들
  4. 규칙 조정 / 예외 추가
  5. 경보가 믿을 만해진 뒤에야 IPS로 전환

탐지와 대응은 다른 문제이고, 대응을 서두르면 탐지가 망가진다. 기술은 eBPF가 다 해주지만, 이 판단은 사람이 한다.

04퀴즈

O/X를 누르면 바로 채점되고 해설이 열린다. 틀린 문제의 해설이 진짜 공부다.

점수 0 / 10 아직 안 풀었다

A. O / X

01IDS와 IPS는 코드상 반환값 하나 차이일 수 있다.

정답 O. TC_ACT_OK냐 TC_ACT_SHOT이냐다. 기술적 차이는 작지만 운영상으로는 완전히 다른 물건이다.

02IPS는 트래픽 경로 위에 있으므로 자신이 장애점이 될 수 있다.

정답 O. IDS는 죽어도 탐지만 멈추지만, 인라인 IPS가 오작동하면 통신이 멈춘다.

03모드 전환을 위해 프로그램을 다시 컴파일하고 재부착해야 한다.

정답 X. iconfig 맵으로 런타임에 바꾼다. IDS → IPS 승격을 트래픽 중단 없이 하기 위해서다.

04UDP 페이로드는 이더넷 14 + IP 20 + UDP 8 = 42바이트 뒤부터 시작한다.

정답 O. IP 헤더가 옵션 없이 20바이트라는 가정이 들어 있다. 정석은 IHL을 읽는 것이다(09번 참고).

05bpf_skb_load_bytes()의 크기를 변수로 넘겨도 verifier는 문제 삼지 않는다.

정답 X. 크기가 0이 될 수 있으면 invalid zero-sized read로 거부된다. 하한이 1 이상임을 증명하기가 까다롭다.

0614번이 4바이트 고정 청크로 스캔하는 것은 성능 최적화 때문이다.

정답 X. verifier 제약 때문이다. 크기가 컴파일 타임 상수여야 증명할 게 없어진다. 제약이 설계를 결정한 사례다.

07시그니처가 두 패킷에 걸쳐 있으면 이 방식으로 탐지할 수 있다.

정답 X. 커널에서 재조립을 못 한다. 단편화는 시그니처 기반 탐지의 대표적 회피 기법이다.

08TLS로 암호화된 트래픽의 페이로드도 TC 훅에서 검사할 수 있다.

정답 X. 안 보인다. 실무에서는 TLS 종단 이후에 검사하거나 uprobe로 SSL_write를 잡아 평문을 본다(04번 확장).

09실무에서는 IDS로 충분히 관찰한 뒤에 IPS로 승격하는 것이 정석이다.

정답 O. 오탐이 있는 상태로 차단을 걸면 정상 트래픽이 끊긴다. 09·10·12번이 전부 같은 이야기를 한다.

10페이로드 앞 40바이트만 스캔하는 것은 회피에 완전히 안전하다.

정답 X. 시그니처를 뒤로 밀면 통과한다. 처리량과 탐지율 사이의 거래이고, 실무 IDS도 대부분 앞 N바이트만 본다.

B. 빈칸 채우기

코드를 보지 않고 먼저 답해 보고, 눌러서 확인한다.

C1TC 훅에서 패킷을 실제로 버리는 반환값은? 
return TC_ACT_SHOT;   /* IPS 모드 */
/* IDS 모드면 TC_ACT_OK */

이 반환값 하나가 탐지와 차단을 가른다. 나머지 엔진은 동일하다.

C2페이로드 시작 오프셋은 어떻게 계산되나? 
#define ETH_HLEN 14
/* 14 (이더넷) + 20 (IP) + 8 (UDP) = 42 */

IP 헤더 20바이트 가정이 들어 있다. 옵션이 있으면 어긋나므로 정석은 IHL을 읽는 것이다.

C3invalid zero-sized read 에러를 피하려면? 
/* 크기를 컴파일 타임 상수로 고정한다 */
__u32 chunk = 0;
bpf_skb_load_bytes(skb, off + i, &chunk, 4);

변수 크기로 읽으면 verifier가 "1 이상"을 증명하지 못한다. 상수면 증명할 것이 없다.
